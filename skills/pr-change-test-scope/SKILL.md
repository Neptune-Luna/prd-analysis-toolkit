# PR 改动与测试范围

收到链接即开始。去重后逐个分析 PR，有业务关联时合并梳理联测范围。

## 核对代码

1. 读取每个 PR 的状态、目标分支、最新提交和差异，并取得远端当前 main。优先用已连接的仓库工具或已认证的 Git；私有仓库网页返回 404 时，通过已有本地仓库或远端 Git 读取目标分支和 refs/pull/<编号>/head，保持原工作树不变。Actions 链接先查运行对应的分支、提交和关联 PR，查不到关联 PR 时按运行提交界定范围。
2. 默认以远端当前 main 核对主线影响。目标为 main 的未合入 PR，优先用 Git 合并预览与 main 比较，确认实际增量。目标为 dev 等非主线分支的 PR，先按实际目标分支的 PR 差异辨认本次改动，再核对与 main 的关系，避免把整个目标分支的历史差异算入 PR。已合入的 PR 查实际合入提交及合入前基线。有冲突时说明对应组合及可确认范围；缺源码或基线时列明缺口。
3. 从差异追到实际入口与调用方，核对最终保留的逻辑及配置、权限、状态、兼容和共用入口。多端变更按操作、保存、回读、预览和导出等实际链路核对，涉及模板时同时核对输入、版式和输出。查证明确的配套 PR 与目标分支，并说明它在当前分析中的角色。适用时提示联测应使用的组合，区分源码比对与实际部署证据。

## 输出

使用简单中文、短句、标题和项目符号。默认用两块内容，采用分层列表。

- **代码改了什么**。每个 PR 一个条目，用「所属端 + PR 编号」作标签，一两句概括主要受影响功能和业务逻辑。合并相关改动，链接放在该条目末尾。跨分支或配套版本会影响联测时，在这一块末尾加一小段「联测版本」。
- **建议测试范围**。按「所属端 → 所属页面或实际入口 → 对应功能」组织，后端无页面时使用业务模块或接口，模板用预览、生成或导出入口。每项给出功能名和简短描述，具体到受影响的区域、操作和业务边界。按实际差异展开有意义的功能分支，例如权限和状态、旧数据兼容、异常回读、预览和下载、一致性及公共入口回归。跨端场景归到用户操作入口，后端组补充独有的保存、校验或同步范围，模板组展开独有的版式和输出范围。省略测试步骤、测试数据、用例和验收清单。

末尾注明核对的基线和 PR 提交，并区分代码梳理、历史验证记录与本次实际执行的测试。
