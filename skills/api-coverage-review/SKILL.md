# 需求—技术—用例一致性评审

把需求文档、技术/API 文档和测试用例归一化为可追溯证据，逐项判断接口设计是否覆盖业务规则和测试场景。始终分开报告“文档设计是否覆盖”与“真实实现是否已验证”。

## 适用边界

在以下任一情形使用本技能：

- 用户要求比较需求文档、技术文档、接口文档、测试用例中的至少两类材料。
- 用户询问技术方案或接口设计是否满足需求、验收条件或测试场景。
- 用户要求生成需求—接口—用例追溯矩阵、覆盖率或差异清单。
- 用户要求找出遗漏接口、字段冲突、错误码缺口、孤立用例或超范围实现。

不要在以下情形启动本技能：

- 只分析一份新需求或 PRD：使用 `requirement-analysis`。
- 只查询一个既有业务规则：使用 `business-logic-query`。
- 只生成测试用例且没有比较技术方案的诉求：使用 `requirement-analysis`。

只有一类输入时，先说明缺少比较基准并请求补充。已有两类材料时可以开始，但必须把缺失维度标成证据缺口；三类齐全时才给出完整的一致性结论。

## 不可违反的结论边界

1. 技术文档只能证明“文档描述的设计”，不能单独证明代码已经实现。
2. 只有实际代码、真实接口响应、日志或已执行测试结果被读取并核验后，运行态结论才可写为“已验证”。
3. 测试用例表达预期场景，不自动等同于已批准需求。无需求依据的用例标记为“无需求依据”，不得反向虚构需求。
4. 技术方案不覆盖强制需求时标记为“不满足”；证据不足时标记为“无法判断”，不得用经验补齐事实。
5. 默认只读。发现差异后输出修改建议，不自动修改需求、技术文档、测试用例、代码或云端数据。

## 输入与证据盘点

开始时建立材料清单，至少记录：

| 类型 | 位置 | 标题/版本 | 更新时间 | 实际读取范围 | 可用性 |
|------|------|-----------|----------|--------------|--------|
| 需求 | URL/路径 | 标题或文件名 | 可获取时记录 | 章节、页码或工作项范围 | 完整/部分/不可读 |
| 技术 | URL/路径 | 标题或文件名 | 可获取时记录 | 接口、数据模型、时序范围 | 完整/部分/不可读 |
| 用例 | URL/路径 | 标题或文件名 | 可获取时记录 | Sheet、目录、用例范围 | 完整/部分/不可读 |

按 [source-ingestion.md](references/source-ingestion.md) 读取不同来源。附件、图片、嵌入表格或画板不可读取时，明确记录证据缺口，不得静默跳过。

证据优先级为：

1. 用户本轮明确确认；
2. 最新生效且已批准的需求或评论；
3. 需求正文；
4. 技术设计或接口文档；
5. 测试用例和历史资料。

技术文档负责解释实现设计，不能覆盖或改写需求；测试用例中的新增预期只能作为待确认假设。

## 标准工作流

### 1. 建立运行目录

在当前工作区创建：

```text
artifacts/<YYYYMMDD-HHmm>-<项目slug>-api-coverage/
```

所有中间产物和最终报告写入该目录。项目名无法确定时使用来源标题的简短 slug，不使用 `project`、`temp` 等无意义名称。

### 2. 归一化需求

生成 `_requirements.md`，为每条可测试需求分配 `RQ-001` 起的稳定编号。每条至少包含：

- 规则或验收条件；
- 适用角色、前置条件和触发条件；
- 主流程、异常、边界、权限、状态或数据约束；
- 优先级或强制性；
- 精确来源：文档、章节、页码、URL 或工作项位置；
- 歧义和待确认项。

不要把背景、目标或建议直接当成强制接口要求。

### 3. 归一化技术契约

生成 `_technical-contract.md`，为接口或关键技术行为分配 `API-001` 起的稳定编号。按 [api-coverage-checklist.md](references/api-coverage-checklist.md) 提取：

- 接口名称、方法、路径、内容类型和版本；
- 鉴权、授权、数据隔离；
- 请求字段、类型、必填性、枚举、范围、格式和默认值；
- 响应结构、空值、缺省字段、兼容性；
- HTTP 状态、业务错误码、错误消息和重试语义；
- 状态流转、幂等、重复提交、并发和事务；
- 副作用、异步任务、消息、审计和可观测性；
- 性能、安全、分页、过滤、排序及限制；
- 精确来源和证据完整度。

文档只写“按规则处理”但未定义规则时，记录为缺失，不做有利推断。

### 4. 归一化测试场景

生成 `_test-scenarios.md`，为每条独立场景分配 `TC-001` 起的稳定编号。拆分复合用例，至少记录：

- 场景名称和类型：正常、异常、边界、权限、状态、并发、兼容性等；
- 前置条件、输入或操作；
- 预期响应、状态或副作用；
- 优先级；
- 关联需求（能确认时）；
- 精确来源：文件、Sheet、行号、目录或用例编号。

无法找到需求依据时保留场景，但标记为“无需求依据”。

### 5. 建立双向追溯矩阵

按 [comparison-model.md](references/comparison-model.md) 生成 `traceability-matrix.md`，至少包含：

| 需求ID | 需求摘要 | 技术证据 | 用例ID | 设计覆盖结论 | 运行态结论 | 差异/证据 |
|--------|----------|----------|--------|--------------|------------|-----------|

必须同时完成两种检查：

- 正向：每条需求是否有技术契约和测试场景覆盖。
- 反向：每条测试场景是否有需求依据和对应技术行为。

额外列出：未覆盖需求、孤立用例、技术超范围行为、相互冲突的预期、重复或不可执行用例。

### 6. 逐接口评审

围绕每个接口串联需求与场景，不只比较关键词。至少判断：

- 请求能否表达需求所需的全部条件；
- 校验规则是否覆盖合法、非法和边界输入；
- 响应能否支撑页面、流程和测试断言；
- 错误码能否区分业务失败原因；
- 权限和数据范围是否符合角色要求；
- 状态、幂等、并发、事务和副作用是否闭环；
- 兼容性、性能、安全和可观测性是否满足明确要求。

### 7. 输出最终报告

生成 `final-report.md`，固定包含：

1. 执行结论：整体设计覆盖结论、运行态验证状态、是否存在阻断项；
2. 材料与范围：版本、读取范围和证据缺口；
3. 覆盖统计：需求、接口、用例数量及各结论分布；
4. 接口评审：按接口列出满足项、部分满足项和缺口；
5. 差异与风险：阻断缺口、冲突、孤立用例、技术超范围；
6. 运行态验证：已检查的代码、响应、日志、执行结果，或明确写“未验证”；
7. 修改建议：需求、技术设计和用例分别需要补充什么；
8. 来源：文件、链接、章节、Sheet 和版本信息。

如确有代码、响应、日志或测试执行证据，额外生成 `_runtime-evidence.md`；没有运行态证据时不要创建空文件。

### 8. 校验产物

运行：

```powershell
node "skills/api-coverage-review/scripts/validate-review.mjs" "<RUN_DIR>"
```

校验失败时修正文档后重跑。不可通过删除真实缺口、虚构 ID 或改写结论来满足校验器。

## 结论词汇

设计覆盖结论只允许使用：

- `满足`：技术文档有明确且一致的证据覆盖规则和场景。
- `部分满足`：只覆盖部分条件、分支、字段、错误或副作用。
- `不满足`：技术设计与强制需求冲突，或明确缺少必需行为。
- `无法判断`：技术证据不足、版本未知或材料不可读。
- `无需求依据`：测试预期找不到有效需求依据。
- `技术超范围`：技术行为找不到需求依据，需确认是否保留。

运行态结论只允许使用：

- `已验证`：已核验代码、真实接口结果、日志或已执行测试证据。
- `未验证`：仅有文档或静态推导。
- `验证失败`：实际证据与预期不一致。

整体结论不得只看百分比。任何 P0/P1 强制需求为“不满足”，都应列为阻断项。

## 输出质量要求

- 每个结论都能追溯到需求、技术和用例中的具体位置；没有证据的一侧明确留空并解释。
- 覆盖率分母、分子和排除项必须写清楚，不把“无法判断”计为“满足”。
- 区分事实、推导、假设和建议。
- 同义字段需记录映射依据；仅名字相似不能视为同一业务含义。
- 发现版本冲突时先报告冲突，不擅自选择对结论最有利的版本。
- 不长篇复制原文，使用准确转述和短引用定位。
- 用户指定输出目录、文件名或模板时，以用户要求为准，同时保留上述核心字段和结论边界。
