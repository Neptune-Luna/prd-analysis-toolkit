# 比较与判定模型

## 比较单元

不要按文档段落做机械相似度比较。以“可测试业务规则或场景”为最小单元，将三类证据映射到同一语义：

```text
RQ（需求规则） → API（技术契约） → TC（测试场景）
       ↑                                  ↓
       └──────── 反向检查需求依据 ────────┘
```

一条需求可映射多个接口和用例；一个接口或用例也可覆盖多条需求。矩阵中使用逗号分隔多个 ID，不因多对多关系复制或丢弃证据。

## 语义匹配步骤

对每个比较单元依次核对：

1. 主体：角色、租户、组织、资源所有者是否一致；
2. 条件：前置状态、输入、权限、时间和数据范围是否一致；
3. 行为：创建、查询、更新、删除、计算、通知等动作是否一致；
4. 结果：响应、状态流转、持久化、副作用和错误是否一致；
5. 约束：类型、枚举、边界、唯一性、幂等、并发和性能是否一致。

任何关键维度不一致都不能判为完全满足。

## 设计覆盖结论

| 结论 | 适用条件 | 示例 |
|------|----------|------|
| 满足 | 技术文档明确覆盖全部强制条件和预期 | 需求要求重复提交不产生重复订单，接口定义幂等键及相同结果返回 |
| 部分满足 | 主流程存在，但异常、字段、权限或边界不完整 | 定义了创建接口，但未定义超限错误码 |
| 不满足 | 明确冲突，或强制行为完全缺失 | 需求禁止跨租户查询，接口却允许传任意租户 ID |
| 无法判断 | 缺少技术证据、版本不明或内容不可读 | 只写“服务端校验”，没有校验规则 |
| 无需求依据 | 用例预期无法追溯到有效需求 | 用例要求自动重试三次，需求未提及 |
| 技术超范围 | 技术行为无法追溯到需求 | 方案新增自动删除数据的接口，无业务依据 |

缺少证据与明确缺失要区分：文档目录承诺后续补充但当前无内容通常是“无法判断”；方案明确没有必需能力或定义相反行为是“不满足”。

## 运行态结论

| 结论 | 最低证据 |
|------|----------|
| 已验证 | 读取到相关代码路径并能追踪关键分支，或观察真实接口响应/日志，或有可信的已执行测试结果 |
| 未验证 | 只有需求、方案、接口定义或未执行的测试用例 |
| 验证失败 | 真实实现、响应、日志或测试结果与设计预期不一致 |

静态接口定义、OpenAPI 文件和技术评审结论都属于设计证据，不属于运行态证据。

## 覆盖统计

至少报告：

- 需求总数及满足、部分满足、不满足、无法判断数量；
- 有测试覆盖的需求数与未覆盖需求数；
- 用例总数及有需求依据、无需求依据数量；
- 技术行为总数及技术超范围数量；
- 已进行运行态验证的比较单元数量。

推荐公式：

```text
设计完全覆盖率 = 满足的需求数 / 纳入评审的需求总数
测试需求覆盖率 = 至少关联一个有效用例的需求数 / 纳入评审的需求总数
运行态验证率 = 运行态已验证的比较单元数 / 纳入运行态检查的比较单元数
```

在报告中列出分子、分母和排除项。不得把“部分满足”或“无法判断”计入完全覆盖。

## 差异优先级

- `P0`：安全、权限隔离、资金/核心数据损坏、法规或关键主流程完全不可用。
- `P1`：强制需求不满足、重要异常无处理、状态或事务无法闭环。
- `P2`：边界、兼容性、提示、可观测性或非关键场景缺口。
- `P3`：文档表达、命名、低风险冗余或优化建议。

优先级由影响决定，不因“只是文档缺失”自动降级；接口契约不明确可能直接阻断开发和测试。

## 冲突处理

1. 先记录冲突双方的原始来源、版本和更新时间。
2. 按证据优先级判断是否存在明确的生效版本。
3. 无法确定时标记“待确认”，不要选择更完整或更容易测试的一方。
4. 报告冲突影响到的接口、需求和用例 ID。
5. 给出可直接发送给产品、开发或测试负责人的完整确认问题。
