# 最终需求分析报告结构与写作规范

用于 AGGREGATE 阶段生成可独立阅读、可直接用于评审会议的 `final-report.md`。参考报告体现的是质量标准，不要求机械复制业务内容或固定编号风格。

## 必需结构

### 1. 项目概览

- 背景与目标：说明为什么做、面向谁、解决什么问题。
- 交付面与范围：按端、系统或模块列出本期交付和明确排除项。
- 当前状态：工作项状态、优先级、计划版本、部署/提测证据；未提供时明确标注。
- 证据基线：用表格列出来源、版本/时间、读取范围和用途，并说明缺失的设计稿、原型、接口或测试证据。

### 2. 需求萃取

至少覆盖业务需求、用户/角色、功能需求和非功能需求。每类内容区分：

- 已确认：原文明确或多来源一致。
- 冲突/未确认：不同来源不一致，或会改变数据模型、主流程、权限、状态机和验收预期。
- 测试推导：为了可测试性提出但尚未确认的异常、边界、性能、安全和可观测性要求。

字段、接口、枚举、默认值、权限和状态适合用表格表达；不要为了套表格而拆碎自然流程。

### 3. 分析与评价

以下五个维度必须分别出现：

1. 完整性：主流程、异常、空态、权限、并发、删除/恢复及依赖是否闭合。
2. 一致性：列出一致项和冲突项；冲突写明双方来源及影响。
3. 合理性：区分合理设计和风险/反模式，说明判断依据。
4. 量化性：先列已确认数值，再列建议讨论的阈值；经验值明确标为建议，不作为原始验收要求。
5. 逻辑闭环：按实体描述状态、转换、逆向操作、失败恢复和数据回写缺口。

### 4. 澄清结论

- 先给文档成熟度和红/黄/绿数量统计。
- 再逐条内嵌全部澄清问题；每条至少包含唯一编号、优先级、来源/场景、完整问题和主要影响。
- 问题应能由产品或开发独立回答并关闭。不得用主题词、汇总句或中间文件链接替代明细。

### 5. 评审意见

- 明确需求类型和结论，例如通过、有条件通过或不建议进入下一阶段，并写清条件。
- 产品与开发确认项分开，避免责任人不明。
- 给出按模块/链路组织的回归范围。
- 变更需求若存在历史用例或接口资产，增加“既有资产处置”，明确保留、修改、新增、降级或废弃。
- 提供可直接口头使用的评审会发言稿，聚焦最影响决策的冲突和阻塞点。

### 6. 来源追溯与产物

链接原始来源和 `_extraction.md`、`_clarifications.md`、`_review.md` 等过程产物，说明未读取或未验证的范围。若本次未生成测试用例，要明确说明，不得让读者误以为已交付。

## 写作规则

- 先写结论，再写证据和影响；避免只罗列页面文案。
- 同一结论只能处于一种证据状态：已确认、冲突/未确认或测试推导。
- 冲突必须保留双方表述及来源，产品未裁决前不得代替其选边。
- 报告应脱离 `RUN_DIR` 中间文件仍可理解和用于会议；过程文件用于追溯，不用于补正文缺失。
- 章节可按项目复杂度合并子节，但不得删除五维分析、完整澄清明细、评审结论和来源限制。
