# Neptune 上线内容说明

## 固定偏好

- 默认组织为 `neptune-robotics`，每次实时枚举全部可访问仓库，不固定为历史任务中的三个仓库。
- 默认中文，面向客户经理、AM、产品和业务人员，按业务模块合并跨仓库功能；正文不放代码、提交哈希、PR、内部技术证据。
- 标题与文件名为 `YYYY年M月D日版本更新内容说明.html`，日期使用本次**上线日期**，不能用执行日期代替。缺少日期先询问，同时继续仓库盘点。
- 默认自包含 HTML：左侧固定目录、当前章节高亮、窄屏顶部目录、截图点击放大、打印/保存 PDF。复用 `assets/release-template.html` 的版式，不复用上次正文或截图。
- 默认只展示上线日期，不展示“待上线／已发布”、测试进度、P0 数量或各功能当前交付状态；用户明确要求时才加入。报告本身的制作、审核、发布等业务状态仍需说明。本次历史任务的日期、分支、作业编号都不是后续默认值。
- 截图账号默认 **`luna-am`**，优先复用有效会话。环境取用户当前指定地址；历史测试地址为 `http://192.168.2.74`，每次核对是否仍对应本次版本。缺密码时询问，已有授权则直接使用；不把密码存入 skill、脚本、证据文件或正文。
- 交付放当前任务 `outputs/`；内部清单、差异和截图原件放 `work/`。不自动部署、创建 release、修改仓库、发布飞书或发送消息。

## Git 范围与完整性

1. 沿用本次会话已经确认的上线日期、目标分支/版本、基线信息，只询问仍不明确且影响范围的事项。
2. 用 GitHub connector 或已认证 `gh` 分页实时枚举全部仓库；可运行 `scripts/inventory_repos.py --org neptune-robotics --out work/repos.json`。包括归档仓库并判定是否相关；权限不足、API 失败应列为覆盖缺口，不能称为全量。
3. 每仓库记录目标 ref/SHA、上次实际正式发布 ref/SHA、来源及变更结论。检查发布记录、tag、部署配置；排除草稿、预发布和其他组件的 tag。不能机械把最新 tag、main 或 dev 当作发布状态。单仓库多组件按组件判断。
4. 用户给出统一分支时，逐仓库检查存在性，不存在不能无声换成 dev/main。缺发布基线时询问，未解决的仓库标记范围待确认，继续处理已确定的仓库。
5. 固定目标 SHA，以 `git diff base target` 的最终树差异判断交付功能，结合 `git log base..target` 理解过程；不要只读提交标题，也不要用 merge-base 差异冒充两个发布版本差异。分叉、回滚、浅克隆缺历史需核实。
6. 优先独立只读 checkout，不强制切换用户工作区、不覆盖未提交文件。GitHub diff 如有分页/文件截断，改用本地 git，避免遗漏；无需给所有仓库安装依赖。
7. 所有枚举到的仓库均应有内部结论：有业务变化 / 仅内部变化 / 无变化 / 不适用及原因 / 无法确定。文档不附此技术清单，但最终说明未解决的缺口。

## 功能梳理

从最终差异核对前后端入口、状态、权限、校验、feature flag。合并同一业务能力，排除撤销、仅测试或未进入本次部署的功能；后台实现不能凭空推断 App 已提供按钮。

用户提供需求链接时读取全文并核对最终实现，尤其是状态切换时机、排序字段、时间口径和数量限制。需求与实现不一致时内部记录差异，正文按核实的当前实现说明，不把需求计划写成已有能力，不默认加入“待验收确认”。无法确定且影响使用的内容应明确询问或说明缺口。内部保留证据，业务正文只写功能内容。

每项功能说明：

- **主要变化**：原来怎样、现在怎样、用户获得什么。
- **谁来用 / 在哪里**：端、角色、真实菜单路径与按钮名。
- **怎么用**：前提、按顺序操作、字段含义、完成后看到什么。
- **规则与异常**：已核实且影响使用的状态、权限、边界和核对方式。
- **对应截图**：当前实际页面及简明图注，不能让读者照抄示例数据。

订单按预约、查询、确认、代建、取消、付款细化。其他模块同样展开，状态和排序变化应单列，不埋在“体验优化”里。没有独立界面的稳定性修复说明无需操作即可，不伪造截图。

## 面向业务的文案组织

- 参考文档：https://neptunerobotics.feishu.cn/wiki/BM0Ywyl5Hi8cv5kNekkcTYd2nwd 。可访问时读取其结构；不可访问时说明，不能声称已参考正文。
- 开头用“一句话看完”和“要做什么／现在去哪／操作重点”入口表概括，再按实际使用场景展开，最后整理有帮助的常见问题。
- 章节名称注明所属端或菜单，不能只写脱离页面的需求名。具体操作说明以当前页面为准，明确立即保存、手动通知、草稿与发布等容易误解的行为。
- 交付详细 HTML 时同时提供可复制的群公告简述，按“本次发版内容 → 运营平台／Client APP／系统维护 → 1）功能 → A. 变化”组织，省略不存在的分类，不自动发送。用户只要求修改现有文档时不必重复整段公告。
- 用户排除某功能时同步清理正文、总览、目录、FAQ、专属截图及简述；当次排除不自动成为以后版本的固定排除规则。

## 当前环境实拍

使用正式浏览器/计算机工具，读取工具说明，依据新鲜 DOM/无障碍状态和截图操作。可从源码定位页面路由，但必须在真实页面验证。

- 默认 `luna-am`，确认环境与本次版本相符。不能拿旧文档图、组件演示、mock 页面或 AI 生成图当实拍。必须用旧图时，先说明缺口并取得用户同意。
- 用户明确要求从前端代码截图时，可运行目标版本连接授权环境，并标注本地运行页面；要求“当前环境实拍”后直接使用部署环境。
- 用户给出可用作业时优先使用，不固定历史作业 1160。数字 mobi ID 与 Unique ID 可能不同，列表无结果时核对路由，不能穷举编号。
- 只导航、筛选、展开、查看。不要点保存、加减、确认付款、审核、完成、取消订单或发布等写数据控件。**梯度加减立即提交修改，不是预览。**
- 浮层可能遮住类型切换按钮。先在确认安全的空白处收起浮层，读取状态确认关闭，再开另一个面板；不要点击被浮层盖住的按钮。截图前核对面板标题。
- 如出现意外数据变化，停止写操作，记录对象与变化并告知用户；不要反向点击尝试恢复，比例归一化不一定可逆。
- 登录页、错误页、空白图或关键控件截断不算功能图。会话失效或无权限可合理恢复；无法解决须明确缺图，不改权限、不造图、不宣称全部完成。
- 记录图片对应模块、日期、环境、页签/记录与范围；保留原始截图，不更改图中按钮或数值，避开凭据及敏感联系信息。

## 生成文档

整理 `work/release-content.json`，调用：

```text
python <skill-dir>/scripts/render_release.py --input work/release-content.json --output-dir outputs
```

输入示例（日期必须替换，图片相对 JSON；`html` 是编写者控制的正文，不直接拼接未经处理的外部文字）：

```json
{
  "release_date": "2026-10-10",
  "released": false,
  "show_release_status": false,
  "intro": "本次业务变化概述。",
  "modules": [{
    "id": "orders",
    "title": "订单管理",
    "blocks": [
      {"html": "<h3>功能名称</h3><p class=\"where\">入口说明</p><p>主要变化</p><ol><li>操作步骤</li></ol>"},
      {"image": "screenshots/orders.png", "title": "页面名称", "caption": "来源和操作说明"}
    ]
  }]
}
```

按功能位置交错安排图片与文字，不把全部截图堆在末尾；总览、使用须知和 FAQ 按需要编写，不凭空添加功能或限制。图片嵌入 HTML，单文件可分发。

## 交付检查

核对所有仓库结论与模块覆盖；上线日期、标题和文件名一致；截图日期保持实际拍摄日期，修改上线日期不能一起改写截图日期；无上轮日期、旧数量限制或已删除按钮。目录锚点、章节高亮、窄屏目录、放大和打印正常，图片加载且对应功能。用浏览器视觉检查排版。

用户后续补充日期、需求或截图时增量更新原文件，保留其他已确认内容。最终给交付链接及必要说明；未解决的仓库或截图缺口必须明确，不声称已完整完成。
