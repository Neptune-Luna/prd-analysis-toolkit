# 【Client APP】客户反馈功能（照片维度）需求评审报告

## 需求类型

**判定：** 变更需求。

**依据：** 本需求在既有 APP 图片详情、`inspection_report`、mobi 后台 AM 配置中心、客户/AM 权限体系和多张存量业务表上增加照片反馈能力，不是独立新系统。

**提问策略：** 重点审查旧接口兼容、现有图片详情交互、报告查询性能、后台权限与筛选、存量用例修订和跨模块回归；同时追问三项核心口径冲突。

**总体结论：** 有条件通过，暂不建议直接冻结验收基线。技术方案已达到可开发粒度，但重复反馈、选择“是”的提交行为、客户名称筛选对象尚未统一；在这三项结论确认前，数据库、接口和既有测试用例可能互相证明对方“错误”。

## 一、流程合理性

### 已发现断点

| # | 断点位置 | 问题描述 | 评审建议 |
|---|---|---|---|
| F1 | APP 点击反馈后 | 没有正式定义提交中、成功、失败、超时的 UI 状态，失败时本地选中态可能与服务端不一致。 | 冻结“先本地更新还是成功后更新”、按钮禁用、Toast、失败回滚和重试策略。来源：萃取 1.1、澄清 R-E2。 |
| F2 | APP 再次进入照片 | 技术方案依赖 `inspection_report` 回显，但未定义缓存和写后读一致性。 | 明确写成功后刷新方式、允许的不一致窗口和缓存失效规则。来源：澄清 Y-S3。 |
| F3 | 后台客户名称筛选 | 页面需求是名称筛选，列表接口只收 userId，中间的客户搜索接口未写入主流程。 | 把“名称输入→搜索选择→ID 过滤”作为正式闭环，补接口和重名处理。来源：萃取 1.2、澄清 R-D1。 |
| F4 | 后台无权限/无负责客户 | 接口分别可能报无权限或返回空页，但入口显隐、空态区分未定义。 | 定义角色入口矩阵和“暂无负责客户/暂无反馈/无权限”三种状态。来源：澄清 Y-E3。 |
| F5 | 后台照片查看/下载 | 只描述点击放大、右键下载，没有缩略图失败、原图过期、触屏下载替代路径。 | 增加图片加载失败、重新签名、显式下载按钮和权限校验。来源：澄清 Y-E2、G-E2。 |
| F6 | 多表补全异常 | 船名、部位、反馈人、OSS 任一关联缺失时接口行为不明。 | 规定单行降级或整页失败，并固定缺省字段协议。来源：澄清 R-E3。 |
| F7 | 测试环境交付 | 评论说合并后自动部署，但没有部署成功和版本证明。 | 将构建号、服务版本、部署时间、数据库变更状态作为提测入口条件。来源：澄清 R-D3。 |
| F8 | 反馈数据消费 | 需求背景是收集识别反馈，但当前流程在 AM 列表结束，没有进入产品/算法改进的闭环。 | 明确本期是否只收集展示；若需算法消费，另列数据流、指标和失败补偿。来源：澄清 Y-D3。 |

### 逻辑冲突

| # | 涉及的规则 | 冲突描述 | 评审建议 |
|---|---|---|---|
| C1 | 重复反馈 | 产品评论要求追加多条；技术方案和接口附件要求唯一键覆盖。 | 必须由产品最终裁定并回写正文；若追加，技术方案的数据模型、查询回显和列表展示均需重做。来源：澄清 R-S1。 |
| C2 | “是”的提交语义 | 技术方案要求是/否均写入；既有 XMind 认为“是”不提交。 | 以产品确认后的接口语义统一 APP 与 46 条用例，禁止两套预期并存。来源：澄清 R-S2。 |
| C3 | 客户名称 vs userId | 页面筛选概念与接口实际过滤维度不一致。 | 明确筛选客户组织、客户账号还是反馈人，并选用 organizationId/customerId/userId 中正确主键。来源：澄清 R-D1。 |
| C4 | 反馈时间 | 表有 create_at/update_at，列表伪代码按 create_at 排序，但重复修改后的“反馈时间”不明确。 | 明确展示/排序字段；追加历史与覆盖最新两种模式分别给出时间定义。来源：澄清 R-S3。 |
| C5 | 权限范围 | 原需求只写管理员和对应客户主/辅 AM；技术方案让 am_admin 查看全部。 | 形成角色—入口—数据范围矩阵并由产品确认。来源：澄清 R-D2。 |
| C6 | 未反馈编码 | 技术方案内部以 0 表示未反馈、JSON 省略字段；接口附件要求前端不要按 0 判断。 | 开发需用真实序列化回归证明字段省略，防止不同网关/生成器返回 0。来源：萃取 1.2。 |
| C7 | 历史用例的额外功能 | 既有用例包含 URL 参数保持、反馈时间/内容等额外筛选，正文无这些需求。 | 标记为建议范围，不得因为实现缺失直接判缺陷。来源：萃取“增量对照”。 |
| C8 | 照片删除策略 | FK 禁止物理删除、业务表软删除，但反馈可见性和图片缺失处理未定义。 | 补照片/出动删除后的 APP、后台与数据保留规则。来源：澄清 Y-S1。 |

### UX 死角

| # | 位置 | 问题 | 评审建议 |
|---|---|---|---|
| U1 | APP 反馈入口 | 原需求仍保留“长按？增加反馈入口？”文字，缺最终交互稿。 | 给出按钮位置、文案、未选/选中/加载/失败状态。 |
| U2 | APP 四按钮 | 用户切换已提交结果是否需要确认未知，误触可能覆盖既有反馈。 | 根据追加/覆盖规则决定是否二次确认或提供撤销。 |
| U3 | APP 网络失败 | 若选中态不回滚，用户会误以为已提交；若直接回滚又可能不知原因。 | 使用可观察失败态和明确重试入口。 |
| U4 | 后台客户搜索 | 重名客户/多个账号可能无法区分。 | 搜索结果展示组织名、账号和唯一标识，且数据源受权限过滤。 |
| U5 | 后台空列表 | “无负责客户”“筛选无结果”“确实无反馈”可能显示同一空白页。 | 分别设计空态文案和清空筛选 CTA。 |
| U6 | 图片查看器 | 仅右键下载可发现性差，触屏不可用。 | 在放大预览中提供显式下载按钮和加载失败提示。 |
| U7 | 权限入口 | 非授权角色若能看到 Tab 再报错，属于“先显示后拦截”。 | 前端按角色隐藏入口，后端仍做强制鉴权。 |
| U8 | 反馈内容 | 后台用枚举拼展示文案，未知反馈类型可能显示空白。 | 增加未知类型兜底文案和监控。 |

## 二、量化性要求

下表阈值均为经验建议，不是已确认需求；需产品/开发确认后才能用于验收。

| # | 原文模糊/缺失项 | 来源位置 | 要求量化 | 建议阈值 |
|---|---|---|---|---|
| Q1 | 写反馈响应时间未定义 | 萃取 1.4 | 明确 P95 响应时间与超时 | 普通请求 P95 < 500ms；超时阈值单独确认 |
| Q2 | 列表响应时间未定义 | 澄清 Y-B2 | 明确首屏和翻页 P95 | 普通查询 P95 < 500ms |
| Q3 | 最大反馈量未定义 | 澄清 Y-B2 | 明确单客户/全量数量级 | 万级数据至少验证索引和稳定分页 |
| Q4 | pageSize 上限未定义 | 澄清 R-B2 | 明确最小/最大值 | 默认 20，建议上限 100 |
| Q5 | 客户搜索触发规则未定义 | 澄清 Y-B1、G-B1 | 明确最少字符、防抖、结果上限 | 最少 1–2 字符、防抖约 300ms、结果不超过 50 条 |
| Q6 | 重复点击窗口未定义 | 澄清 R-E1 | 明确按钮禁用和幂等窗口 | 请求发出后立即禁用，到成功/失败结束 |
| Q7 | 图片规格未定义 | 澄清 Y-B3 | 明确格式、大小、分辨率 | 由现网照片上限给定；大图应使用缩略图加载 |
| Q8 | 图片 URL 有效期未定义 | 澄清 Y-E2 | 明确过期时长和刷新机制 | 至少覆盖页面会话时长，过期后可重新签名 |
| Q9 | 写后读一致性未定义 | 澄清 Y-S3 | 明确最大状态同步延迟 | 无缓存时应立即一致；有缓存需明确秒级上限 |
| Q10 | 反馈时间格式未定义 | 澄清 G-B2 | 明确时区和精度 | 统一 Asia/Shanghai 或 ISO 8601 带时区，至少到秒 |
| Q11 | 数据保留期未定义 | 澄清 G-S2 | 明确当前状态/历史/日志保留期限 | 若需要审计，建议不少于 90 天，最终按公司策略确认 |
| Q12 | 可用性与错误率未定义 | 萃取 2.4 | 明确成功率、监控阈值 | 关键写接口成功率目标建议 ≥99.9% |

## 三、隐性需求

| # | 显性描述 | 推导的隐性需求 | 依据 |
|---|---|---|---|
| H1 | 客户可对照片反馈 | 服务端必须校验照片真实归属，防止枚举照片 ID 越权。 | 技术方案已考虑；需要安全回归。 |
| H2 | AM 仅看名下客户 | 搜索候选、列表数据、图片下载都必须执行同一行级权限，不能只过滤列表。 | 防止通过 userId/mobiId/URL 绕权。 |
| H3 | 重复反馈可修改或追加 | 必须定义审计、时间和历史策略。 | 修改会影响追溯和客户争议。 |
| H4 | `inspection_report` 增加字段 | 所有旧客户端必须忽略未知字段；旧报告类型和三个调用路径需要回归。 | 向后兼容与调用链完整性。 |
| H5 | 批量查询反馈 | 必须避免逐照片 N+1，并验证大 mobi 图片量下性能。 | 报告接口为高频读路径。 |
| H6 | 后台多表补全 | 需要批量查询、缺失值协议和数据一致性策略。 | 船名、部位、用户、OSS 来自多表。 |
| H7 | 图片放大/下载 | 原图下载需要鉴权、短期 URL、日志脱敏和失败重签名。 | 敏感客户照片与链接安全。 |
| H8 | 关键反馈操作 | 需要结构化日志和错误监控，但日志不得记录 JWT 或完整签名 URL。 | 可观测性与数据安全。 |
| H9 | 反馈类型可扩展 | 旧客户端/后台遇到未知枚举必须有兼容策略。 | 灰度发布和前后端版本差异。 |
| H10 | 工作项处于测试中 | 提测必须包含数据库迁移、接口版本、APP 包、后台前端版本和可用账号数据。 | 变更跨四个交付面。 |
| H11 | 现有 46 条用例 | 核心语义确认后必须批量修订，而不是只追加新用例。 | 历史预期已与技术方案冲突。 |
| H12 | 客户反馈用于改进识别 | 需要定义本期是否有数据消费、统计指标和负责人。 | 否则业务目标只完成“收集”，未形成应用闭环。 |

## 建议回归范围

1. APP 图片详情：作业中与已完成、不同照片类型、未反馈/单维度/双维度/修改状态、网络和会话异常。

3. `inspection_report`：新增字段省略语义、所有报告构建路径、旧客户端兼容和性能。
4. mobi 后台：入口/角色、客户搜索、mobi 精确查询、组合筛选、分页排序、空态、图片操作。
5. 数据层：追加或覆盖模型、时间字段、软删除、关联数据缺失、多表批量补全和索引。
6. 安全：跨客户照片 ID、跨组织筛选、复制图片 URL、非 AM 访问、日志敏感信息。
