## 维度 1：分析与评价

### 1.1 完整性评价

#### 已覆盖主流程

1. APP 用户在单张照片上分别反馈海生物识别、漆况识别的准确/不准确。
2. 写接口从登录态解析用户，按照片真实归属做权限校验，不信任客户端传入 mobi ID。
3. `inspection_report` 返回两个维度的当前反馈结果，未反馈维度通过字段缺失表示。
4. mobi 后台反馈列表展示 mobi ID、船名、时间、照片、部位、反馈人和反馈内容。
5. 后台支持客户名称筛选和 mobi ID 精确查询，并按管理员/AM 角色做行级权限隔离。

#### 已描述但存在冲突的主规则

| 规则 | 来源 A | 来源 B | 当前判定 |
|---|---|---|---|
| 同一照片同一维度重复反馈 | 2026-08-03 产品评论：生成多条反馈，不覆盖 | 技术方案 revision 17、接口附件：唯一键 upsert，覆盖上次结果 | 🔴 未决冲突，影响数据模型、列表条数、反馈时间与历史追溯 |
| 选择“是”是否提交 | 技术方案/接口附件：四个按钮每次点击都提交 | 既有 XMind：选择“是”不提交，只有“否”提交 | 🔴 既有测试资产与当前技术方案不一致 |
| 客户名称筛选对象 | 产品评论：按客户名称筛选 | 技术方案：名称搜索后传反馈人 `userId` | 🔴 “客户组织名称”与“反馈人账号名称”是否同一筛选维度未明确 |

#### 异常与分支覆盖

| 异常/分支 | 文档覆盖 | 评价 |
|---|---|---|
| 照片不存在或已软删除 | 部分覆盖 | 写接口定义参数错误；错误码和客户端提示未定义 |
| `feedback_type`、`accurate` 非法枚举 | 接口附件覆盖 | 只说明参数错误，未给 code/message 契约 |
| 越权反馈 | 覆盖 | 服务端从照片反查 mobi 并校验权限，设计合理 |
| 重复点击/并发提交 | 未覆盖 | 唯一键可避免重复行，但最后写入胜出规则、请求防抖和用户反馈未定义 |
| 网络超时/断网 | 未覆盖 | 对照 exception-scenarios.md，缺少加载、重试、失败回滚和本地选中态处理 |
| 会话过期 | 未覆盖 | 未定义跳转登录后是否恢复照片和待提交选择 |
| 后台无权限 | 部分覆盖 | 定义权限错误，但页面入口隐藏还是点击后拦截未定义，存在“先显示后拦截”风险 |
| AM 未绑定客户 | 技术方案覆盖 | 返回空页；页面空态和引导未定义 |
| 筛选无结果 | 接口附件覆盖 | 返回 `total: 0`；页面文案和重置入口未定义 |
| 图片 URL 失效/下载失败 | 未覆盖 | 缩略图、原图加载失败、鉴权与 URL 有效期未定义 |
| 关联照片/船舶/部位数据缺失 | 未覆盖 | 列表批量补全失败时整页失败、单行降级还是跳过未定义 |

#### 字段完整性

写接口三个字段的类型、必填性和枚举已明确；查询侧两个反馈字段的三态编码已明确。后台列表响应样例提供了主要字段，但 `position` 的具体字段名仍注明“实现时对齐”，反馈时间取首次 `create_at` 还是最近 `update_at` 未明确。

### 1.2 一致性评价

#### 一致项

- 产品评论、技术方案、接口附件和既有用例均指向两个反馈维度：海生物识别与漆况识别。
- 2026-08-06 产品评论确认 mobi ID 只需精确查询，与技术方案和既有用例一致。
- 技术方案与接口附件对 `feedback_type=1/2`、`accurate=1/2`、未反馈字段不返回的定义一致。
- 工作项、技术方案和接口附件均要求管理员/对应 AM 的数据隔离。

#### 不一致项

1. **数据保留策略冲突**：产品评论要求追加多条，技术实现只保留每维度最新状态。
2. **APP 提交语义冲突**：历史用例把“是”作为不提交状态，技术接口要求“是”和“否”都提交。
3. **时间字段冲突**：表同时有 `create_at` 和 `update_at`；列表伪代码按 `create_at DESC`，但响应字段叫“反馈时间”，重复修改后是否显示/排序最近修改时间不清楚。
4. **筛选语义冲突**：页面概念是“客户名称”，接口参数却是“反馈人 userId”；一个客户可能有多个账号，同名账号也可能属于不同组织。
5. **权限命名差异**：原需求写“管理员和对应客户的主/辅 AM”，技术方案增加 `am_admin` 看全部；需要确认 `am_admin` 是否属于需求中的管理员。

### 1.3 合理性评价

#### 合理设计

- 写接口不接收 mobi ID，而是由照片反查真实归属，可降低伪造 mobi ID 绕权风险。
- 两个反馈维度按类型拆行，使反馈类型可扩展，读接口使用三态值表达未反馈/准确/不准确。
- 查询批量合并反馈结果，避免三个调用点重复补逻辑。
- 后台按 `organization_id` 做权限过滤并建立索引，符合列表查询模式。

#### 反模式风险

| 风险 | 对照经验库 | 说明 |
|---|---|---|
| 点击后无明确反馈 | anti-patterns.md“无反馈操作” | 成功 Toast、提交中禁用、失败恢复均未形成正式需求 |
| 入口可见后才报无权限 | anti-patterns.md“先显示后拦截” | 后台 Tab 的角色显隐规则未定义 |
| 空列表无引导 | anti-patterns.md“无空状态” | 接口只返回空列表，页面空态未定义 |
| 图片加载失败无错误态 | anti-patterns.md“无错误态” | 缩略图/原图失败降级未定义 |
| 复杂筛选依赖隐式二次接口 | anti-patterns.md“隐藏关键信息” | 客户名称到 userId 的映射契约未写入正式接口说明 |

### 1.4 量化性评价

#### 已量化内容

- 列表默认页码 `current=1`、默认 `pageSize=20`。
- 枚举范围：`feedback_type` 仅 1/2，`accurate` 仅 1/2。
- 未反馈字段整体省略，避免 0 与字段缺失的双重语义。

#### 未量化内容

| 项目 | 当前缺口 | 经验建议（非已确认需求） |
|---|---|---|
| 写接口响应时间 | 未定义 | 普通写请求可先以 500ms 作为评审基线 |
| 列表响应时间与最大数据量 | 未定义 | 普通查询 500ms、单页 20–50 条作为评审基线 |
| 重复点击间隔 | 未定义 | 提交后立即禁用，防重复请求 |
| 图片加载/下载 | 未定义大小、超时、URL 有效期 | 明确缩略图大小、原图上限、超时和重试 |
| 客户名称搜索 | 未定义最少字符、延迟和结果上限 | 搜索 300ms、下拉结果上限需产品/开发确认 |
| 反馈数据保留 | 未定义保留期限 | 若采用追加历史，需定义审计和清理策略 |

### 1.5 逻辑闭环评价

#### 单照片、单反馈维度状态机

```text
未反馈
  --选择“是”并提交--> 准确
  --选择“否”并提交--> 不准确

准确
  --再次选择“否”--> 不准确
  --再次选择“是”--> 准确（幂等写）

不准确
  --再次选择“是”--> 准确
  --再次选择“否”--> 不准确（幂等写）
```

| 检查点 | 当前定义 | 缺口 |
|---|---|---|
| 初态 | 未反馈字段不返回 | APP 未加载完成时与真正未反馈如何区分未定义 |
| 正向转换 | 是/否均可提交 | 与既有用例“是=不提交”冲突 |
| 逆向转换 | 技术方案允许覆盖修改 | 与产品评论“追加多条”冲突 |
| 幂等 | 唯一键 upsert | 并发写入顺序、版本控制和客户端重复点击未定义 |
| 删除 | 表支持 `delete_at`，FK 为 NO ACTION | 谁能删除反馈、删除后列表/APP 状态如何变化未定义 |
| 时间 | 首次 `create_at`、修改 `update_at` | 列表显示和排序采用哪个时间未闭环 |

## 维度 2：软件需求定义

### 2.1 业务需求

- **背景：** 客户 ONE 在演示中希望对检测照片的识别结果提供反馈入口。
- **核心目标：** 让客户对单张照片的海生物识别和漆况识别给出准确/不准确反馈，并让内部管理员/AM 在后台查看和筛选反馈。
- **业务价值：** 收集照片级识别质量反馈，支持产品和算法后续改进；后台统一查看客户反馈并联系相关客户。
- **当前阶段：** 工作项处于测试中，代码已合并；部署成功与最终上线验收尚无明确证据。

### 2.2 用户需求

| 用户角色 | 用户任务 | 权限范围 | 来源 |
|---|---|---|---|
| 客户 APP 用户 | 查看照片并分别反馈海生物/漆况识别是否准确；再次进入查看当前反馈状态 | 只能反馈当前账号有权访问的 mobi 下照片 | 需求概要、技术方案、接口附件 |
| 管理员 | 查看、筛选全部客户反馈，放大或下载原图 | 全部组织 | 需求概要、技术方案 |

### 2.4 非功能需求

#### 已确认约束

- 写接口不能信任客户端提供的 mobi ID，必须从照片反查并校验权限。
- 后台查询必须按组织做服务端行级过滤，不能只依赖前端隐藏。
- `mobi_photo_id` 有外键约束；照片软删除后写接口需排除。
- 列表查询为分页接口，并为 mobi ID、organization ID 建立索引。
- API 未反馈状态通过字段缺失表达，需要保持前后端序列化一致性。

#### 测试推导、待确认

- **安全性：** 校验跨客户照片 ID 越权、AM 篡改 userId/orgId、下载原图 URL 越权和过期访问。
- **一致性：** APP 当前状态、写接口落库和后台列表必须在一次成功反馈后最终一致。
- **并发：** 同一照片同一维度并发选择相反结果时需有确定的胜出规则或版本冲突策略。
- **可用性：** 提交中应防重复点击；失败不能留下看似成功的本地选中态。
- **性能：** `inspection_report` 新增批量查询不得退化为逐照片 N+1；后台补全船名、部位、用户和 OSS 也应批量查询。
- **可观测性：** 写入失败、权限拒绝、列表补全失败应有可定位日志，但日志不得泄露照片 URL/JWT。

2. 客户名称筛选用例应拆分为“客户搜索接口的名称模糊匹配”和“列表接口按返回 userId 精确过滤”，并确认搜索目标是组织还是反馈人账号。
3. “URL 参数保持”“其他筛选字段（反馈时间、反馈内容等）”属于现有需求未确认范围，应降为建议或删除确定预期。

### 建议新增覆盖（测试推导）

- 写接口非法枚举、照片不存在/软删除、跨客户越权、会话过期。

## 萃取阶段结论

需求的技术实现路径已较完整，接口字段、数据库模型、APP 查询回显和后台列表主体均有明确设计；但目前不能直接按“需求已完全明确”进入稳定验收，原因是三项核心语义仍存在冲突：

1. 重复反馈追加多条还是覆盖最新状态；
2. 选择“是”是否同样提交；
3. 客户名称筛选的实际对象及名称到 `userId` 的映射。

这些冲突会同时影响数据库结构、接口行为、列表数量、反馈时间以及至少一批既有用例。建议在进入正式回归前优先确认；本阶段暂不生成澄清清单和评审结论，等待用户确认萃取结果后再继续。
