> **本文讲什么**：Neptune 运营后台是内部同事用来「管一次出动从建单到交付报告的全过程」的云端网页系统。本文按运营人员能感知的功能逐项说明：做什么、给谁用、有哪些业务规则、有哪些限制。
>
> **写给谁**：全团队——产品、UI、测试、前端、后端，以及新同事和 AI 助手。
>
> **与已有文档的关系**：本文是**独立完整**的运营后台产品说明，读它不需要先读别的文档。跨产品线的边界口径以《产品线依赖地图》为准，全局术语与命名陷阱汇总见《Neptune 产品文档总索引》第 3 章。
>
> **术语**：出动（Mobi，一次上船作业的完整单据）、三板（左舷 Port Side / 右舷 Starboard Side / 底板 Flat Bottom）、检测线 L1–L10（每块板划成的若干条线，机器人沿线行进拍照）、特殊部位（Niche Areas，三板之外的部位，如螺旋桨、艏侧推、舭龙骨、海底门、舵、艉架、球鼻艏）、R0–R4 污损等级（对客的污损口径，R0 无污损到 R4 重度）、洗前/洗后（清洗前后的两组对照数据）、AM（客户经理）、报告员（专职制作清洗报告的角色）、边缘侧（船上的作业平台与机器人）/云端侧（本后台与云端服务）。完整对照表见《Neptune 产品文档总索引》第 3 章。

> **产品线范围**：运营后台前端 + 后端的云端服务（运营后台能力面）+ 云端 helix 平台的若干应用（网关、流程编排、权限、定时任务、抽帧与 AI）+ 独立的展会服务。上一代的 admin 服务是旧链路的计算 sidecar，**正在退役、无前端直连**，本文不再展开。

## 阅读正文要知道的几个技术词

正文尽量用业务话讲，但下面这几个词绕不开，它们直接决定了「谁负责、出问题查哪一侧」。

| 词 | 一句话解释 | 对使用者意味着什么 |
|---|---|---|
| **helix** | 云端后端里的一套微服务平台，报告、评级、流程编排、定时任务、权限都跑在上面 | 说「helix 那边」时，指的是云端算报告和跑定时任务的那一片 |
| **OSS（对象存储）** | 照片、视频、PDF、压缩包这类大文件的仓库 | 后台里的图片和下载链接都是「临时签名链接」，会过期，过期重新进页面即可 |
| **PDF 截图式生成** | PDF 不是排版程序生成的，是用无头浏览器打开报告网页再「截」出来的 | 报告网页长什么样，PDF 就长什么样；报告页显示有问题，PDF 一定同样有问题 |
| **定时任务平台** | 一个统一的调度中心，按周期唤起「生成 PDF」「发提醒邮件」「打包照片」等后台作业 | 这类动作不是点完立刻完成，而是排队执行，通常几分钟 |
| **Temporal（流程编排引擎）** | 后端正在迁入的一套出动流程状态机 | 目前生产界面用的还是旧那套口径，两套并存（见 2.2） |
| **Mobi（出动）** | 一次上船作业的完整单据，贯穿建单到交付 | 排查任何问题都先拿出动的 Unique ID 去各端对照 |

## 1. 产品定位与用户角色

> **本章小结**：运营后台是云端的内部作业中枢；系统里有 13 个角色，但角色只是身份标签，真正决定「能看什么、能点什么」的是权限系统，且其中三个角色（财务、报告员、报告组长）在后端被硬性限制了能访问的范围。

### 1.1 一句话定位

运营后台是**云端侧的内部作业中枢**：所有出动的建单、调度、审批文件、现场进度回填、检测/清洗结论核对、报告制作与发布，以及客户、船队、船舶、设备、提醒邮件、年度订单等主数据的维护，都在这里完成。

它不直接操作机器人（那是 NOS 与 BOS 的事），也不面向客户（那是 Client App 的事）。运营后台产出的数据，一端下发给船边作业平台，一端呈现给客户 App。

### 1.2 用户角色

系统内共定义 **13 个角色**：

| 中文名 | 在运营后台的定位 | 对使用者意味着什么 |
|---|---|---|
| 管理员 | 看全部数据、全部菜单 | 出现「别人看不到我能看到」时，先确认对方不是管理员 |
| AM（客户经理） | 主力用户：建单、推进流程、审核检测报告；**只看本组织下客户的数据** | AM 说「列表是空的」，多半是他所在组织没绑客户，而不是系统坏了 |
| AM 管理员 | 管理 AM、看全部菜单 | — |
| 调度 | 作业许可、作业安排、建飞书作业群 | 建群按钮只有调度和调度管理员能点 |
| 调度管理员 | 管理调度、维护作业群默认拉人配置 | — |
| 作业队长 | 作业队主数据（后台不单独维护，靠给账号打角色） | 想「新增一个作业队长」，去用户管理里加角色 |
| 作业队员 | 同上 | 同上 |
| 申报人 | 报关/申报（后台无专属页面） | 这个角色目前在后台没有落地页面 |
| 报告员 | 制作清洗报告；**受限角色**，只能进 AI 报告管理相关页面 | 报告员反馈「点什么都 403」属预期，见 2.1 |
| 报告组长 | 给报告员分配报告、冻结/解冻；**受限角色** | 唯一能分配和冻结报告的角色 |
| 财务 | **只能看出动列表 + 改自己密码** | 财务反馈打不开出动详情是设计如此 |
| 访客 | 无角色的用户会被自动补成访客 | 新账号忘了配角色就会变成访客 |
| 客户 | **不是运营后台用户**，是 Client App 账号，被限定只能登 App | 客户账号在后台登录页永远登不进来 |

- 一个用户可以有多个角色；登录后返回的角色字段是中文名逗号拼接。
- 「是否内部员工」的判定：除客户、访客、**报告组长**外都算员工。**报告组长被漏在员工判定之外**（待确认，见第 5 章）。
- 注册权限有层级：只有管理员能注册调度管理员；管理员 + 调度管理员能注册调度；管理员 + AM 管理员能管理 AM。
- **角色只是身份标签，不参与权限判定**——能看什么菜单、点什么按钮由权限系统决定。前端代码里明确写了「禁止用角色做权限判定」。

## 2. 核心功能

### 2.1 登录、权限与菜单

> **本章小结**：登录后菜单和按钮都由后端下发，前端照单渲染；后端另有一道「受限角色白名单」硬门禁；AM 只能看到自己组织下客户的数据。

#### 做什么
账号密码登录，登录后系统给这个人下发「他能看的菜单」和「他能点的按钮」两份清单，前端照单渲染。

#### 给谁用
全部内部员工。客户账号登不进来——客户被限定只能登客户 App 平台（系统里的平台共四种：作业平台 / NMS / 客户 App / BOS）。

#### 业务规则

**登录**

- 密码在前端先做一次 MD5 再传，后端强校验必须是 MD5 格式，否则登录失败。
- **连续 5 次密码错误锁定账号**，计数窗口 1 小时；锁定后**没有自动解锁**，必须找管理员。提示原文：`因账号密码多次输入错误，已锁定，请联系管理员`。
- 禁用账号提示原文：`该账号禁用中，请联系管理员`；无任何角色的账号也登不进。
- 登录态 **7 天**，**不允许多端同时登录**（后登录的会把前一个挤掉）。
- 登录态失效时后端返回业务码 **999**，前端弹「登录已过期，请重新登录」并跳登录页。

**首次登录强制改密**

- 判定条件：账号处于「未激活」状态**且**带「需重置密码」标记，两者同时满足才强制。状态正常的账号即使残留着历史的「需重置密码」标记，也直接进入系统（飞书缺陷 7018701728）。
- 未激活账号除改密动作外，访问任何功能都会被拒并强制登出。
- 改密成功即同时把账号激活。
- 密码复杂度要求：**同时含大写字母、小写字母、数字、特殊符号**，提示原文 `需要包含大小写英文、数字、特殊符号`；两次不一致提示 `两次密码输入不一致`。⚠️ **该校验只在前端做，后端不校验复杂度**（待确认，见第 5 章）。

**菜单（页面级权限）**

- 菜单不是写死在前端的，而是登录后向后端要一棵菜单树，前端按树渲染路由与侧边栏。
- **后端菜单树优先**；只有拿不到（未初始化 / 请求失败）才回退到前端内置的静态菜单。
- 菜单字典共 **25 条**，角色白名单 **3 条**，白名单只覆盖三个受限角色：
  - 财务 → 作业、作业设置
  - 报告员 → AI 报告管理、报告管理、报告制作页
  - 报告组长 → 上述三项 + 操作记录
- 管理员 / AM 管理员**直接返回全量菜单**，不查白名单。
- 取菜单失败时**降级为空树**（看不到 ≠ 越权），不会误放权。
- 顶级菜单及排序：作业(10)、设备管理(20)、AM 配置中心(30)、调度配置中心(40)、管理员权限(50)、AI 报告管理(60)、新加坡展会(70)。其中「消耗记录」和「报告制作」是隐藏节点——能直接访问、但不出现在侧边栏里。

**按钮级权限**

按钮权限按「资源 + 动作」组织，全集 7 项：

| 权限 | 谁有 | 对使用者意味着什么 |
|---|---|---|
| 查看报告 | 报告员、报告组长 | — |
| 编辑报告 | 报告员、报告组长 | — |
| 撤回报告 | 报告员、报告组长 | — |
| 分配报告 | **仅**报告组长 | 报告员看不到「分配」按钮是正常的 |
| 冻结**和**解冻（共用一项） | **仅**报告组长 | 两个动作不拆开，因为前端只需要把这组按钮和「分配」区分显隐 |
| 出动列表查看 | 财务 | 财务唯一能看的业务页 |
| 年度订单查看 | — | 目前未分配给任何角色 |

精确数字：**报告员 3 项、报告组长 5 项**。

**受限角色的接口白名单（硬门禁）**

除了菜单和按钮，后端还有一道中间件：如果一个用户的角色**全部**落在受限集合内，那么只有白名单里的能力能用，其余一律拒绝：

- **财务只允许两件事**：查出动列表、改自己的密码。
- **报告员 / 报告组长共用一条规则，只允许四类能力**：报告管理（读与写）、审计日志、前端权限配置、改自己的密码。代码注释明确写了「报告制作页的能力本轮明确不放开，后续按 403 反馈补」。
- 混合角色（如 财务 + 报告员）不属于任一受限子集 → **放过**。业务约定不应出现这种配置。
- 被拦下时返回的是英文原文 `role allowlist: forbidden`，业务码 2005。

**AM 只看本组织客户的数据**

- 管理员看全部；AM 只看自己所在船队（组织）下的客户。
- 出动列表同样按组织过滤：AM 先查自己所在的组织，再取这些组织授权的船舶与出动。**组织为空时直接返回空列表**。
- 调度看到的是「待定 + 近 1 年及未来」的出动。
- 财务的出动列表可见范围由权限服务单独判定。

#### 限制

- 后台是**两套权限体系并存**：云端服务侧的会话式登录 + 角色白名单中间件（宽进严出、判定失败时放过），helix 侧的策略式权限（判定失败时拒绝）。两者通过能力转发与缓存里的「账号失效」标记联动。策略改动 **30 秒内**自动热生效，不需重启。
- 权限策略要在两处同时维护（业务侧的镜像数据与权限引擎的规则数据），只改一边会导致「界面显示的权限」与「实际权限」不一致。
- 一个已知陷阱：只配了权限规则、漏配角色绑定时，财务的出动列表会**返回空列表而不是 403**，看起来像「没数据」而不是「没权限」。

### 2.2 出动（Mobi）全流程管理

> **本章小结**：出动是运营后台的主线单据。列表 + 右侧滑出的流程面板，页签跟着出动状态走；状态机目前有两套并存的口径（生产在用的 15 状态口径，和正在迁入的 9 状态引擎口径）。

#### 做什么
「作业 → 作业设置」是运营后台的主战场。列表展示所有出动，点任意一行右侧滑出**流程面板**（宽度占屏 72%），面板按流程环节分页签，逐环节填报与推进。

#### 给谁用
AM（建单、推进、检测报告）、调度（许可、安排、建群）、财务（只读列表）。

#### 出动列表

列：Unique ID（可一键复制，成功提示「已复制」）、船名、作业地点、出动类型、出动任务、当前状态（带底色标签）、ETB（值为 0 时显示「待定」）、AM、调度。「清洗标准」和「执行方式」两列代码里已经写好但被注释掉，**当前不展示**。

筛选：船名、IMO（只允许数字）、跟单客服（多选）、调度（多选）、ETB 区间；**ETB 区间跨度上限 364 天**，输入防抖 300 毫秒。另有状态快捷筛选：全部 / ETB≤2天 / 待抵达 / 检测中 / 清洗中 / 报告生成中 / 已结束。

分页默认每页 10 条。**财务角色点击行不会打开详情抽屉。**

#### 新建出动

必填：下单人、跟单客服、船名、作业地点、ETB、是否需要在 APP 展示、出动任务（部位 × 仅检测/仅清洗 的级联多选）、执行方式、出动类型、作业标准。**当执行方式同时包含「游泳机器人」和「N0 或 Magneto」时，额外必填「检测方案版本」**（10 条线版 / 5 条线版）。

关键校验文案原文：

- ETD 早于或等于 ETB → `ETD不能早于ETB`
- 海底门 / 螺旋桨数量类 → `请输入数量`、`请输入大于0的整数`
- 点「待定」按钮会把 ETB 设为当前时间并禁用 ETD
- 成功 `添加成功`，失败 `添加失败，<后端原因>`

**出动类型 6 种**：1 仅检测 / 2 仅清洗 / 3 先检后洗 / 4 先检待洗·直接清洗 / 5 先检待洗·最多洗单侧板 2 个 80m 地图 / 6 先检待洗·等 AM 清洗通知。⚠️ **前端新建表单不提供「仅清洗」选项**。

**执行方式 5 种**：Magneto / C5 / 游泳机器人（Blue ROV）/ 潜水员（Diver Team）/ N0。**作业标准 4 种**：纳百 / 澳大利亚 / 新西兰 / 巴西。

#### 流程面板：状态与页签的对应关系

出动状态共 **15 个有效值**，流程面板的页签与状态**一一对应**——面板上出现哪几个页签，由后端返回的流程数组决定，前端只是按数组顺序把页签摆出来。

| 状态值 | 状态名 | 对应页签 | 该环节填什么 | 对使用者意味着什么 |
|---|---|---|---|---|
| 1 | 待开始 | 待开始（基础信息） | 出动基础信息 | 刚建完单的默认状态 |
| 2 | 作业许可 | **审批文件** | 搭靠证、海事备案、码头备案等 | 页签名和状态名不同名，沟通时注意 |
| 3 | 出动安排 | 作业安排 | 人员、工作船、遥控箱、时间、作业群 | **自动建飞书群在这一步触发** |
| 4 | 抵达大船 | 抵达大船 | 实际抵达时间、吃水、能见度、水流 | — |
| 5 | 检测中 | 检测中 | **作业结束时间** | 这个字段是后面报告能否发布/提交的前置条件 |
| 14 | 预览报告 | 预览报告 | 预览报告制作与发布 | 给客户看的初步结论 |
| 6 | 检测报告 | 检测报告 | AM 逐部位审核照片与结论 | 与 14 的「预览报告」最易记混 |
| 15 | 清洗策略 | 清洗策略 | 三板清洗档位与海生物图 | 含检测环节的出动都有 |
| 7 | 出动安排（清洗作业） | 清洗作业安排 | 清洗环节的人员与资源 | 只有被标记为「需单独安排清洗作业」时才出现 |
| 8 | 抵达大船（清洗作业） | 抵达大船 | 清洗环节的抵达确认 | 同上 |
| 9 | 清洗中 | 清洗中 | 清洗作业结束时间、未清洗部位 | 「未清洗部位」有独立保存按钮 |
| 10 | 最终报告 | 最终报告 | 清洗报告审核、最终报告文件流转 | — |
| 11 | 结束 | 已完成（空内容） | — | 页签点开是空的，属正常 |
| 13 | 暂停出动 | 暂停出动 | 暂停原因与描述 | **独立状态**，不是流程节点 |
| 12 | 取消出动 | 取消出动 | 取消原因与描述 | **独立状态**，不可恢复 |

**页签集合是动态的**，规则如下：

1. 固定头四节点：待开始、作业许可、作业安排、抵达大船。
2. 只清洗 → 加「清洗中」；有检测 → 加「检测中」+「清洗策略」。
3. 只有出动被标记为「需要单独安排清洗作业」时，才插入「清洗作业安排」+「清洗作业抵达大船」。
4. **有效出动类型按实际任务反推，不信数据库里存的类型**；两者不一致时会打一条告警日志。
5. 仅检测 → 删掉「清洗中」，追加「预览报告」；仅清洗 → 删掉「检测中」「清洗策略」，追加「最终报告」；先检后洗 → 把「清洗中」移到末尾再追加「最终报告」（需求 7025065922 已删掉先检后洗的「预览报告」节点）。
6. 「检测报告」节点插在「清洗中」之前，适用于除「仅清洗」外的全部出动类型。
7. 末尾追加「已完成」。
8. **旁路截断**：已取消 → 页签截到当前状态、末尾换成「取消出动」；已暂停 → 同理换成「暂停出动」。

页签的样式就是进度语义：当前之前的是已完成、当前高亮、之后是未开始；暂停/取消用红色。只有检测报告、预览报告、最终报告三个页签有底部操作栏。

#### 暂停 / 恢复 / 取消

面板顶部随时可暂停、恢复、取消，**三者都必填描述**。

- **暂停原因 3 种**：突发事件 / 天气、水况恶劣 / 其他。
- **取消原因 6 种**：客户自身原因取消 / 官方手续不批准 / 突发事件 / 天气、水况恶劣 / 船体过脏 / 其他。
- **「待开始」和「作业许可」两个阶段不允许暂停/恢复。**
- 取消时可以勾选「下一程安排」，系统会自动创建下一次出动。
- 取消是**不可恢复**的终态操作；只想暂停或改字段就不要点取消。
- 前端按钮可见性：恢复仅在「暂停」状态可见；暂停在「作业安排」到「最终报告」之间可见；取消在「待开始」到「最终报告」之间且未取消时可见。
- 前端弹窗文案：`请选择暂停原因` / `请输入描述`（占位 `请输入恢复原因描述`）/ `请选择取消原因` / `请选择下一程安排` / `请选择出动地点` / `请选择ETB`；成功 `暂停成功` / `恢复成功` / `取消成功`。
- ⚠️ **后端对暂停/恢复的三类校验（原因非法、描述为空、状态不允许）都返回同一句「请求参数错误」**，运营人员看不出到底是哪一条不满足。

#### 操作记录

每次流程动作都会留痕，共 **16 种操作类型**：编辑、发布、暂停、恢复、取消、更新 ETB、完成备案、更新预计抵达时间、更新实际抵达时间、开始/结束检测、开始/结束清洗、开始/结束制作最终报告、更新障碍船是否影响作业。前端以英文展示（ETB Updated / Port Permit Approved / Neptune ETA / Vessel Arrived / Inspect Start|End / Clean Start|End / Report Start|End / Operation Paused|Resumed / Obstacle Vessel Affects）。

#### 「作业结束时间」——最容易踩的一个字段

它在**「检测中」页签**填（清洗侧在「清洗中」页签填对应的清洗作业结束时间），**不是在报告页里填**。它是报告能否发布/提交的硬前置条件：

- 检测中页签：标签「作业结束时间」，必填红星，格式 `YYYY-MM-DD HH:mm`，不可手输只能选，保存提示 `保存成功`。
- 检测报告发布按钮的禁用原因原文：**`作业结束时间未填写，请填写后发布`**。
- 清洗报告提交审核的禁用原因原文：**`"作业结束时间"尚未填写，请返回"检测中"节点填写`**。
- 报告头部展示的「结束时间」**优先取这个人工录入的值**，而不是预计离港时间。

#### 背后的状态机（Temporal）

出动流程正在向 Temporal 编排迁移。**引擎侧共 9 个 state，界面上是 10 个阶段**——「检测报告」是「预览报告」的界面子节点，没有独立成 state。

**正向边 8 条**：

| 从 → 到 | 触发方式 | 谁能推 |
|---|---|---|
| pending 待开始 → permit 作业许可 | 人工 | 流程管理员（ops_manager） |
| permit → schedule 作业安排 | 人工 | 流程管理员 |
| schedule → arrived 抵达大船 | 业务事件「船舶抵达」 | — |
| arrived → inspecting 检测中 | 自动（延迟 0，立刻跃迁） | — |
| inspecting → preview_report 预览报告 | 业务事件「检测完成」 | — |
| preview_report → cleaning 清洗中 | 人工，**必须走飞书审批卡片闭环** | 流程管理员 |
| cleaning → final_report 最终报告 | 业务事件「清洗完成」 | — |
| final_report → done 已完成 | 人工 | **客户账号** |

- **最后一步结单必须用客户账号**，客服无权独自结单。
- **回退边 6 条**，全部只有流程管理员能操作，且**不支持跨节点回退**，必须逐级退。`inspecting` 回退时**跳过 `arrived`** 直接退到 `schedule`（否则那条自动边会立刻把它弹回来）。
- 回退会重新触发飞书通知卡片，这是**有意为之**，让相关方知道该阶段重新开放。
- **「检测中」有 12 小时硬超时**：超时只推告警卡片到告警群，**不改状态**。回退到「作业安排」再走一遍会**重置这个 12 小时计时**。
- 取消走补偿流程（Saga）：反向回放已发的飞书通知（用取消卡片模板覆盖原卡片），终态写 `compensated`；若有环节补偿失败则写 `compensated_partial`；补偿失败会升级到告警群，告警也失败则落孤儿记录、**要求运维 24 小时内介入**。
- 流程实例状态 6 种：running / completed / failed / cancelled / timed_out / compensated。
- 审计里还有两种「伪流转」记录：权限不足被拒、目标状态非法——状态不变但留痕。
- 终态实例的所有写操作都返回 `409 instance is terminal`；要改数据只能走「补录」能力，且仅管理员可用。

⚠️ **两套口径并存这一事实**：云端服务侧的 15 个状态与 Temporal 侧的 9 个 state 是**两套并行口径，名字不一一对应**（引擎侧没有「暂停」「取消」「清洗策略」这三个 state）。**当前生产在用的是 15 状态那套**（它驱动流程面板）。两套如何收敛见第 5 章待确认。

### 2.3 检测报告（AM 环节）

> **本章小结**：AM 在流程面板的一个页签里，把船边传上来的照片和 AI 初判整理成可交付的检测结论；逐部位审核有照片数门槛，发布前有四道闸。

#### 做什么
把船边传上来的检测照片和 AI 评级，变成一份经人工把关、可以给客户看的专业检测结论。

#### 给谁用
AM。它是出动流程面板里的一个**页签**（不是独立菜单），也是整个前端仓库里最大的一个页面。

#### 页面结构
按部位页签组织，与船体划分一致：船图 / 左舷 / 右舷 / 底板（按检测线展开，每条线下按每米水尺陈列照片）/ 螺旋桨（按叶片）/ 特殊部位（配船型示意图）。页签可新增、删除、拖拽排序。

#### AM 在这里做什么

| 操作 | 规则与限制 |
|---|---|
| 整理照片 | 检查系统自动归位的照片、人工补传、挑选进报告的照片、打质量标记 |
| 标注海生物 | 每张照片可加海生物记录（类型 + 覆盖百分比，**最多 4 条**），双击照片卡编辑；每部位写生物污损小结 |
| 标注油漆 | 标注油漆缺陷类型与覆盖档位，写油漆小结 |
| 处理视频 | 查看检测视频、按时间轴剪辑片段、画质增强 |
| 写检测结论 | 海生物结论按五个部位分别写；油漆结论按三个部位写 |
| 写清洗建议 | **上限 500 字** |
| 逐部位审核 | 每部位独立审核状态（橙点待审核 / 绿勾已通过），支持勾选多部位批量审核通过 |
| 开关水印 | 时间戳水印、部位名水印，按检测线级别开关 |

#### 审核的硬性门槛

**批量审核时的照片数下限（前端拦）**：非默认特殊部位要 **2 张**，其余要 **6 张**；不足时提示原文 `以下部位照片数量不足，无法审核：<部位>（N/M张）`。

**后端权威口径**：默认下限 **2 张**；6 个默认特殊部位（球鼻艏 / 艏侧推 / 舭龙骨 / 海底门 / 舵 / 艉框）要求 **6 张**。统一提示文案 `审核照片数量不足（需要至少 %d 张，当前 %d 张）`。**照片数不足时，即使开了「免审」也不会自动置为通过。**

**最小线数门槛**：5 条线版要求左舷、右舷、底板**各至少上传 2 条线**；10 条线版要求**各至少 3 条线**。中文提示 `不符合最小线的要求`。

#### 发布检测报告的四道闸

「发布完整报告」按钮的禁用原因，按判定顺序：

1. `数据异常，请刷新后重试`（一级目录只剩「船图」时）
2. `作业结束时间未填写，请填写后发布`
3. `清洗建议未填写，请填写后发布`
4. `存在尚未审核通过的部位，请审核通过所有部位后再发布报告`

唯一例外：**底板 L1 过窄时，L1 可以跳过审核检查。**

#### 审核通过之后

- 系统会问「是否建议客户洗船」。选「建议」，客户 App 端才会出现清洗建议文案和「确认清洗」按钮。
- 结论与清洗建议随之发布到客户端，同时入队生成 PDF（见 2.10）。
- 撤销审核走单独入口；检测线序号越界时会报英文提示 `line %d out of range for vessel_part_id %s`。

#### 限制

- 报告的主存储是文档型数据库（MongoDB），不是业务库。
- ⚠️ **红线：带重建参数的「刷新结论」会先删掉整份报告文档、再按默认值重建，人工编辑的数据（分区日志、审核状态、人工修正记录）全部丢失。** 页面上有二次确认，但操作前务必看清。

### 2.4 预览报告

> **本章小结**：给「先检待洗」类出动用的初步结论，无审核环节，发布前的照片数检查只提示不阻断。

#### 做什么
在检测数据齐了、正式检测报告还没审完时，先给客户出一份「够不够脏、要不要洗」的初步结论，用于「先检待洗」类出动的客户决策。

#### 给谁用
AM 在流程面板的「预览报告」页签制作与发布，绑定出动状态 14。

#### 业务规则

- 它在报告类型里是**独立一类**。
- **它没有独立审核状态**，直接「发布报告」。
- 发布前的照片数检查是**软提示、不阻断发布**：
  - 船图 0 张 → `「船图」部位没有照片,请上传照片`
  - 特殊部位二级 0 张 → `「特殊部位-<部位名>」部位没有照片,请上传照片`
  - 螺旋桨 0 张 → `「螺旋桨」部位没有照片,请上传照片`
  - 其余部位 < 6 张 → `「<部位名>」部位的照片数量低于6张,请上传更多照片`
- **出动类型决定要出哪几种报告**：仅清洗 → 只出清洗报告；先检后洗与三种先检待洗 → 预览报告 + 清洗报告；仅检测 → 检测报告。

### 2.5 清洗报告 / AI 报告管理

> **本章小结**：独立菜单里的一条完整生产线——报告组长分配、报告员制作、提交审核（16 条硬门槛）、AM 在流程面板审核发布、系统自动出 PDF。

#### 做什么
制作最终交付给客户的完整清洗报告，走「分配 → 制作 → 提交审核 → 发布 → 出 PDF」。

#### 给谁用

- **报告组长**：分配报告、冻结/解冻。
- **报告员**：在报告制作页干活、提交审核。
- **AM**：在出动流程面板的「最终报告」页签做审核通过 / 驳回。

⚠️ 与检测报告的区别（新人最易混）：检测报告是出动流程里 AM 的审核环节；清洗报告是独立菜单里报告员的制作发布流程。**两者页面长得很像（共用同一套部位/照片/标注组件），但流程、负责人、目的完全不同。**

#### 报告管理列表

报告状态 **6 种**：

| 值 | 状态 | 含义 | 对使用者意味着什么 |
|---|---|---|---|
| 1 | 未开始 | 出动创建了但还没有照片上来 | 报告文档不存在或状态为空时，列表一律显示这个（飞书缺陷 6988486636） |
| 2 | 部分完成 | 部分内容已具备 | — |
| 3 | 制作中 | 有照片上来了 / 报告员正在编辑 | 驳回后也回到这个状态 |
| 4 | 待审核 | 报告员已提交，等 AM 审核 | ⚠️ 提交动作目前不写这个状态，见第 5 章第 9 条 |
| 5 | 已发布 | AM 在最终报告节点审核通过 | 触发 PDF 生成 |
| 6 | 冻结中 | 暂停一切流转 | 解冻后回到冻结前的状态 |

状态流转的权威口径写在代码注释里：「创建出动无照片 = 未开始 / 有照片上来 = 制作中 / 报告组员点提交审核 = 待审核 / AM 在出动后台最终报告节点点审核通过 = 已发布」。

#### 每行可做的操作与规则

| 操作 | 规则与提示文案 |
|---|---|
| **分配** | 报告组长把报告指派给报告员，支持一次分配多份。分配时会自动补上报告员角色。被分配者若已有全量权限则跳过、不阻断 |
| **撤销分配** | 持全量权限的报告组长**不支持部分撤销**：`reporter %s has wildcard permission, partial revoke is not supported` |
| **编辑** | 进报告制作页；冻结中的报告隐藏此按钮 |
| **撤回** | **只有「待审核」的报告能撤回**，退回「制作中」。文案原文：`当前报告状态不允许撤回，仅「待审核」报告可撤回`（飞书缺陷 7019870543） |
| **冻结** | **只有「未开始」「制作中」能冻结**。文案原文：`当前报告状态不允许冻结，仅「未开始」「制作中」报告可冻结` |
| **解冻** | **只有「冻结中」能解冻**。文案原文：`当前报告状态不允许解冻，仅「冻结中」报告可解冻`。解冻后回到冻结前的状态；若冻结期间有新照片上来则回到「制作中」 |
| **查看** | 只读打开制作页，任何状态都可用 |

**冻结之后谁还能操作**：分配、编辑、撤回三个按钮被隐藏，只留「解冻」和「查看」；**唯一例外是报告组长在冻结态下仍能看到「分配」**。系统管理员即使没有报告域授权也能冻结/解冻（旁路兜底，因为生产环境的管理员账号往往缺这块授权）。

所有操作都记入「操作记录」页，可追溯谁在什么时间做了什么。记录里的账号字段**只有管理员和报告组长可见**，其他角色只看到用户名（飞书缺陷 6988587415）。操作记录的中文文案模板：`将 <出动号> 分配给了 <人>` / `从 <人> 撤回了 <出动号>` / `授予 <人> 报告管理员权限` / `授予 <人> 报告员权限` / `更新报告 <出动号> 状态为 <状态>`。

#### 报告制作页

顶部显示出动编号、清洗标准、船名、港口。主体是部位页签（船图默认页 / 左舷 / 右舷 / 底板 / 螺旋桨 / 特殊部位）。实际出现哪些页签，来自 AM 在检测报告阶段勾选的部位，报告员也可增删和拖拽排序。

每个页签内：整理照片组、上传/管理洗前视频（可控制是否在报告中展示）、核对海生物总览与油漆总览。检测结论可手改也可「刷新」重算（**会覆盖手改，有二次确认**）。**Attention（注意事项/清洗建议）必填，上限 500 字。**

#### 提交审核的 16 条硬性门槛

点「提交审核」前系统逐条检查，**任何一条不满足都不能提交**，并明确告诉你缺什么。

先说清「一组照片」的定义：**同一位置至少 2 张有效照片才算一个完整组；只有 1 张的叫残组。**

| # | 检查项 | 阈值 | 提示文案（原文） |
|---|---|---|---|
| 1 | 作业结束时间 | 必须已填 | `"作业结束时间"尚未填写，请返回"检测中"节点填写` |
| 2 | 海生物检测结论 | 非空 | `海生物检测结论不得为空` |
| 3 | 油漆检测结论 | 非空（若有该板块） | `油漆检测结论不得为空` |
| 4 | Attention | 非空 | `Attention不得为空` |
| 5 | 左舷每条线每米水尺 | **≥ 1 组** | `左舷每条线每米水尺照片不得低于1组` |
| 6 | 右舷每条线每米水尺 | **≥ 1 组** | `右舷每条线每米水尺照片不得低于1组` |
| 7 | 底板每条线每侧（左/右） | **≥ 6 组** | `底板每条线每侧照片不得低于6组` |
| 8 | 螺旋桨完整组总数 | **≥ 叶片数 × 4**（叶片数取 3–7，取不到时默认 4） | `螺旋桨照片不得低于叶片数量*4组` |
| 9 | 特殊部位每个二/三级部位 | **≥ 6 组** | `特殊部位各个二/三级部位照片不得低于6组` |
| 10–16 | 照片必须成组出现（不能有残组），按部位分成 7 条 | 无残组 | `「左舷 <方向>」照片必须成组出现` / `「右舷 …」` / `「底板 …」` / `「螺旋桨 <部位名>」` / `「特殊部位 <二级> <三级>」` |

#### 审核与发布

- AM 在流程面板「最终报告」页签的「清洗报告审核」子页做审核通过（状态置已发布）或驳回（状态置制作中）。
- 审核通过 → 自动入队生成 PDF（见 2.10）。
- 已发布的报告可点「修改报告」退回编辑，改完重走提交发布。

#### 限制

⚠️ 「提交审核」这个动作在代码上只写了「已发布标记」，**没有把报告状态置成「待审核」**。也就是报告员提交后，管理列表里的状态可能仍显示「制作中」。这条待确认（见第 5 章）。

### 2.6 N0 视频报告

> **本章小结**：N0 机型的产出是视频不是照片组，所以单独出一份视频报告，依附检测报告节点、无独立审核。

#### 做什么
N0 机器人的检测产出是**视频**而不是照片组，所以要单独出一份视频报告。客户 App 上会因此多一个「视频报告 / 照片报告」切换页签。

#### 给谁用
运营在检测报告页的视频区剪辑视频片段；成品由客户在 App 看。

#### 业务规则

- 报告类型独立成一类，后台有独立的能力入口。
- 报告文档存在文档型数据库的独立集合里，**每段视频带自己的评级字段**。
- 视频报告按船体分成 **8 段**，播放时进度条与检测数据联动。
- **它没有独立的审核流程**，依附检测报告节点。

### 2.7 照片是怎么来的：抽帧、选图、水印、打包下载

> **本章小结**：报告里的照片来自船边视频抽帧 + AI 打分 + 配额选片；后台可加水印、可整批打包下载（异步任务 + 轮询 + 飞书推链接）。

这一节回答运营人员最常问的问题：「我在报告页里看到的照片，到底是怎么产生的？」

#### 链路总览

有两条来源，按机型分。

**A. ROV（BOS 线，游泳机器人）**

1. 作业队在地面站录视频，同时生成同名的遥测字幕文件（含姿态、深度、舷别、部位、吃水等）。
2. 结束某个部位检测时，地面站把「视频路径 + 字幕路径」交给边缘桥梁服务，由它排队上传到云端对象存储的出动 ROV 照片目录。
3. 云端收到「文件上传完成」消息后开始抽帧：按 **默认每秒 4 帧** 抽成 jpg。
4. 每张抽出的图先过质量模型打分过滤，通过后上传入库，再统一跑一次「七合一」AI（部位识别 / 海生物密度 / 钙质沉积 / 油漆类型 / 油漆面积 / 质量分）。
5. 处理完的总帧数、有效帧数回传给地面站，更新现场界面上的照片计数。

**视频与字幕的配对不靠文件名，靠同一条上报消息里的批次标识。** 照片上的拍摄时间、坐标、水尺都来自字幕解析。

**B. Magneto（NOS 线）**

边缘侧直接拍照并跑一遍本地即时 AI（给现场看），照片按时间/体积/数量窗口打包上传；视频走即时处理，视频与字幕必须成对（《产品线依赖地图》§2.1）。

#### 人工补传照片

- 入口是照片库组件的上传按钮，支持整目录选取。
- **没有条数上限**，改为**并发 3 个**上传 + 单文件失败**自动重试最多 2 次**。
- 单文件大小上限来自服务端：**后端 100 MB，网关 200 MB**。
- 人工上传的照片**豁免配额选片**（一定保留，不会被自动筛掉）。
- ⚠️ 人工上传的文件名是简名（时间戳 + 序号 + 洗前洗后），**不符合录拍照片的 14 字段命名规范**，打包下载时能看出差别。

#### 照片的分类维度

| 维度 | 取值 |
|---|---|
| 来源 | 清水相机 / 黄水相机 / 潜水员 / 人工上传 / 其他 |
| 阶段 | 洗前 / 洗后 |
| 水上水下 | 水上 / 水下（缺省按水下） |
| 照片类型 | 洗前 / 洗后 / 船头水线 / 船中水线 / 大船洗前 / 大船洗后 / 其他 |
| 相机类型 | N1 黄水 / 其他 / ROV 清水 / ROV 黄水 |

#### 选图规则

报告里每组只展示一张代表照片，选哪张由「质量标记」决定：**最干净 / 最脏 / 普通**，默认「普通」。

排序口径：先按污损评级升序（值越大越脏），同评级按质量分降序，同质量按内部序号升序；然后

- 最干净 → 取排序后的头部
- 最脏 → 取尾部
- 普通 → 取中位数附近

已评级的照片不够时，按序号顺序用未评级照片补齐。**报告页每组取 1 张。** 照片库列表侧只重排、不截断。

配额选片的目标张数（可配置，以下是默认值）：**左右舷每条线每米 5 张、底板每侧每条线 25 张、螺旋桨最少 100 张、特殊部位最少 50 张。**

#### 水印

后台可以给照片打两种水印，开关按检测线级别控制：

- **日期戳**：右下角，格式 `2006-01-02`（按 UTC 取日期），默认字号 45、白色。
- **部位名戳**：顶部居中，默认字号 65、白色、带阴影。

实现方式是把水印参数拼进对象存储的图片处理参数里，**参与链接签名，前端无法篡改**。水印文字有硬限制：**明文上限 64 字节，约 21 个汉字**，超长按完整字符截断。时间戳为 0 视为开关关闭、不打戳（否则会渲染成 1970-01-01，飞书缺陷 7019792809）。

前端开关在报告制作页的时间戳工具栏：「洗前时间戳」「Inspection 时间戳」「洗后时间戳」，报告已发布或只读态下禁用。

打包下载的照片另有一种**深度水印**：底部居中，文案 `深度(Depth): X.XXm`；水尺 ≤ 0 时跳过不打。

#### 照片打包下载

小批量直接下载；大批量走异步打包任务，前端轮询进度。

关键数字：

| 项 | 值 | 对使用者意味着什么 |
|---|---|---|
| 条数上限 | **没有硬上限**，超过 5000 张只记一条告警日志、不阻塞 | 大批量可以照常提交 |
| 任务频控 | 每个用户**每分钟最多 10 个**任务，超限提示 `请求过于频繁，请稍后再试（每分钟最多 %d 次）` | 连点会被限流 |
| 失败明细 | 最多回传 **50 条** | 失败很多时只看得到前 50 条 |
| 打包资源 | 内存预算 256 MB，单对象按 8 MB 估算，拉取并发 4 | 大包耗时长属正常 |
| 重试 | 上限 **3 次**，退避 **5 分钟**；重试未耗尽前对外仍显示「进行中」 | 看到「进行中」不代表没失败过 |
| 压缩包保留 | **180 天** | 超期链接会失效，需重新打包 |
| 前端轮询 | 每 **3 秒**一次，上限 **600 次（30 分钟）**，超时提示 `打包超时，请重新尝试`；开始时提示 `照片开始打包，预计需要5分钟` | 关掉页面不影响后台打包 |

- 压缩包文件名规则：`船名_出动UID_日期_时间_一级部位_二级部位.zip`，缺失段用 `UNKNOWN` 占位。
- 打包前会先把人工修正记录应用一遍，保证打进包里的是最终选图。

**取件链接**：

- 前端界面里的下载链接是 **24 小时**有效的临时签名链接。
- 飞书消息里的链接是一个**带签名的稳定跳转地址，有效期 180 天**，点击时后端验签后再当场换成 24 小时链接跳转。
- 验签失败提示 `invalid or expired download token`；产物过期提示 `download not available (task not success or product expired)`。

**打包完成后推给谁**：飞书推给该客户的 **主 AM 和辅 AM**（可配，缺省就是这两类），按飞书主体分组发送——**跨主体不能合批**。卡片文案：有内容时 `编号 + 链接地址：[点击下载](URL)`，无内容时 `本次作业无可下载内容`。同一任务 1 分钟内的重复通知会被去重。

### 2.8 污损（R0–R4）与涂装（Good/Fair/Poor）的核对

> **本章小结**：这两套等级都是**算出来的**，人工只能改输入再重算；污损用阈值、涂装用投票；且系统里同时存在多套等级口径和两套聚合算法，不能混用。

#### R0–R4 是**算出来的，不是录进去的**

**全系统没有任何「直接录入污损等级」的入口。** 运营人员能改的只有「算等级的输入」——也就是每张照片上标注的海生物种类和覆盖百分比——改完由系统重算等级。

算法阈值：

- **分类口径**：黏膜（Slime）算**微观**；钙质沉积、藻类、海草、海鞘、管虫、藤壶、贻贝算**宏观**；「干净」跳过不计。
- **判级**：宏观覆盖率 **> 40%** → R4 重度；**> 15%** → R3 中度；有宏观但 ≤ 15% → R2 轻度；只有微观 → R1 微生物膜；都没有 → R0 无污损。
- **分母口径修正历史**：宏观得分的分母从「全部条目」改成了「宏观条目数」，否则黏膜和「干净」会把宏观评分稀释得偏低（飞书缺陷 7007813275）。

#### 人工修正入口怎么用

AM / 报告员在报告页双击照片卡编辑海生物标注时，系统**不是覆盖原数据，而是追加一条「人工修正记录」**，记录谁、改了哪张照片、哪个部位哪条线哪个位置、改成了什么。读取报告时按顺序回放这些修正记录，得到最终数据再算等级。

同时系统会把「修改前 / 修改后」的数据写进一个 AI 反馈队列，供算法团队做模型迭代。油漆标注同理有一套自己的人工修正记录。

⚠️ **已知踩坑**：修正记录里如果没显式带海生物类型，会被回落成「贻贝」，导致整批物种都变成贝类（飞书缺陷 7005172362）。

#### ⚠️ 红线：带重建参数的「刷新结论」会丢掉所有人工编辑

「刷新结论」类操作如果带上重建参数，会**先删除整份报告文档、按默认值重建**，分区日志、审核状态、全部人工修正记录一并丢失。**这是全系统最需要提前告知运营人员的一条红线。**

#### ⚠️ 两套聚合口径并存

同一份报告里，「部位级评级」和「列表 / 进度条评级」用的**不是同一套算法**，代码里有明确的「不可混用」警告：

1. **部位级**：先剔除占位格，把该部位所有照片的海生物按物种分组求和、再除以有效照片数，得到一份「平均组成」，再对这份平均组成算一次等级。
2. **列表 / 进度条级**：**刻意不用**上面那套，改为逐张照片各自算等级、再对等级求均值——因为「先平均比例再评级」有摊薄风险（大量干净照片会把重污损摊薄，飞书缺陷 7047861151）。底板左右两半各自独立池化、不合并。

对外文档该以哪套为官方口径，见第 5 章待确认。

#### 另外两套等级，不要与 R0–R4 混称

- **边缘侧的污损网格等级**（无数据 / 干净 / 微观 / 轻度宏观 / 中度宏观 / 重度宏观）：阈值同为 15% / 40%，但只看 top3 且排除黏膜与微藻。
- **作业任务里人工录入的 3 档**（1 轻 / 2 中 / 3 重）：这一套是**人工录入的**，与报告的 R0–R4 不是同一套。归属见第 5 章待确认。

#### 涂装评级 Good / Fair / Poor

同样是算出来的，但算法完全不同——**用投票，不用平均**。

**单张照片的评级**：先查缺陷所属「严重等级」，再结合覆盖率档位判级，多个缺陷取最严的一档：

| 缺陷等级 | 缺陷种类 | 判级规则 |
|---|---|---|
| 0 | 无瑕 | 恒 Good，不参与 |
| 1 | 小孔、橙皮、沉积、粉化、褪色 | 覆盖率 **≥ 40%** → Fair，否则 Good |
| 2 | 冷流、剥离、开裂、生锈、磨损、起泡 | 覆盖率 **≥ 40%** → Poor，否则 Fair（**任何占比都至少 Fair，没有 Good 档**） |
| 3 | 损伤 | 覆盖率 **> 15%** → Poor，否则 Fair |

无任何缺陷数据 → Good。

**段级与部位级评级**用同一个投票规则：

- 众数唯一 → 取众数
- 两档平票 → **取更差的那一档**
- 三档 1:1:1 平票 → 取中间值 Fair
- 无有效票 → 无评级

**分段口径**：左右舷固定 3 段（上/中/下），底板固定 2 段（左/右）——⚠️ 注意这是**按拍摄张数顺序三等分 / 对半分的，不是按物理位置算的**。

投票制是 2026 年 7 月才替换掉旧的「均值取整」算法的：均值会把「两 Fair 一 Good」截断成 Good，掩盖较差的实际漆况。**人工改过的段不会被自动重算覆盖。**

⚠️ 生物污损评级用分段均值、涂装评级用分段投票，**两套算法互不影响，不要混用**。若锁死值与投票结果不一致且存在有效投票，系统会打一条告警日志供排查，但**不会自动纠正**。

**油漆缺陷面积四档**：< 5%（视为 good condition，不输出文案）、5–15%、15–40%、40%+。

**钙质沉积三档**：0–15% / 15–40% / 40%+。**钙质沉积只出现在螺旋桨和艏侧推部位**；档位是对该部位各图的档位取算术平均后四舍五入，为 0 则不输出。

**报告里可选的海生物类型是硬编码的 8 类**：贻贝、管虫、海草、海鞘、生物膜、海藻、藤壶（+「干净」，列表时跳过）。仅螺旋桨 / 艏侧推部位追加「钙沉积」。⚠️ 这和后台「海生物配置」菜单里维护的那张清单**不是同一份数据**（见 2.15）。

### 2.9 船体分区的展示口径

> **本章小结**：「报告页上看到的部位页签是谁定的」——这是三层不同的东西，分清楚了才不会找错人。

| 层 | 是什么 | 谁维护 | 对使用者意味着什么 |
|---|---|---|---|
| **① 分区字典** | 全系统可用的部位清单（部位大类、中英文名、用途、排序、螺旋桨命名方式） | 理论上由后台能力维护，**但运营后台没有对应页面**，创建/编辑能力前端零引用 | 想加一个全新部位，目前后台点不了，得找研发 |
| **② 某次出动的实际分区** | 这次出动实际要做哪些部位 + 是清洗还是检测 | AM 在新建出动时勾选「出动任务」 | 出动做错部位，改这里 |
| **③ 报告页签集合** | 某类报告（检测 / 清洗）实际展示哪些页签 | AM 在检测报告阶段勾选，报告员也可增删拖拽 | 报告里少一个页签，改这里 |

**分区不挂在船舶维度**——船舶库里没有「这条船有哪些部位」的配置，分区是挂在「出动 / 报告」维度的。

#### 部位大类（6 类，硬编码）

1 大船（前端叫「船图 / GA Plan」）/ 2 左舷 / 3 右舷 / 4 底板 / 5 螺旋桨 / 6 特殊部位。其中左舷、右舷、底板合称「三板」。⚠️ **同一个部位（编号 1），后端叫「大船 / Vessel」，前端叫「船图 / GA Plan」。**

#### 检测线与特殊部位（口径唯一权威）

- **检测线 Line1 – Line10**，映射成设备协议里的表示是「部位=0，线序号=1..10」。
- **特殊部位有固定编号，设备实时上报和视频对账补齐两条路径共用这份映射**：螺旋桨=5、艏侧推=18、海底门=39、舵=51、舭龙骨=27、艉架=52、球鼻艏=86。海底门再细分高位 / 低位 / 应急 / 其他。
- 检测方案两版：**10 条线版 / 5 条线版**。

#### 螺旋桨叶片命名

两种命名方式：**数字桨片** 与 **字母桨片**，另有「螺旋桨特殊部位」。后台有一个开关用于翻转叶片命名方式。**叶片数取 3–7 片。**

#### 部位用途

每个部位带「用途」标记：检测报告 / 清洗报告 / 通用 / 清洗进度。**污损评级只统计「检测用途」的部位**（飞书缺陷 7007813275）。

#### 运营人员实际的操作入口

在报告制作页里通过「报告工具集」调整：部位树查询、分区落库、分区位置（拖拽排序）、未清洗部位标记、螺旋桨叶片命名开关。

⚠️ 报告实际渲染用的分区数据走 helix 的数据字典服务（另一条读路径），它与分区字典的关系见第 5 章待确认。

### 2.10 报告 PDF 的生成与分发

> **本章小结**：PDF 不是排版生成的，是用无头浏览器打开报告网页截出来的——所以「报告页什么样，PDF 就什么样」。

#### 做什么
报告发布后自动出一份 PDF，登记到出动的「最终报告」环节，并让客户 App 出现「下载报告」入口。

#### 关键认知：PDF 是「用浏览器打开报告页截出来的」

链路（《产品线依赖地图》§2.5）：

1. **入队**：报告发布时，按「出动 + 报告类型」**幂等入队**一条待生成任务（重复发布不会重复排队）。两条触发路径等价：报告员手动发布、AM 审核通过。
2. **执行**：定时任务领取任务，拼出报告页地址（带出动 ID 和报告类型两个参数），用无头浏览器打开这个页面，**按 150% 缩放**截成 PDF。缩放是为了提升 PDF 里图片与文字的清晰度。
3. **上传**：PDF 存到该出动的报告目录下（检测与清洗各一个子目录），文件名带出动 ID 和一个随机串。
4. **回写**：把下载地址写回报告文档。
5. **清洗报告额外一步**：在同一个事务里补写一条「最终报告」类型的出动文件记录（软删旧的 → 写对象记录 → 写文件记录）。原因写在代码注释里：**客户 App 的「作业-最终报告节点」依赖这条文件记录做流转校验**，而 PDF 本身只落在报告文档里（飞书缺陷 6991404447）。

#### 关键数字

- 任务状态 5 种：待处理 / 处理中 / 成功 / 失败 / 死信。
- **重试上限 3 次，退避 5 分钟。**
- 单批并发上限来自配置，**配置为 0 时回退成 1**。
- 每一步失败都只把当前这条任务标记失败并继续下一条，**不会中断整批**。
- 通常几分钟内完成。

#### 运营人员看到的入口

- **报告预览**：在页面里以内嵌方式打开报告页，检测和清洗各有一个预览入口。
- **下载 PDF**：AI 报告制作页的「下载完整报告」、最终报告节点的「下载 PDF」（500 毫秒防抖）。链接不存在时提示 `下载链接不存在`。

#### 报告页里有什么

报告页由公共渲染服务提供，**在线预览和 PDF 两种模式的页面集、顺序、数据完全一致，只有外壳不同。**

页面序（共 31 项模板）：封面 → 运营总结（两页）→ 污损概览封面 → 污损状况定义 → 检查程序 → 污损概览（洗前/洗后/简版/详细，详细分左舷/右舷/底板/螺旋桨）→ 涂装概览封面 → 涂装状况定义 → 涂装概览（简版/详细）→ 检查结果封面 → 对比结果。

按数据动态裁剪与展开：

- **检测报告**：剔除对比结果页与清洗专用的洗前/洗后页；左右舷按每条线水尺从高到低**两张一页**；舭龙骨每侧 **2 张一页**；底板每条线每侧**最多 6 张、每 2 张一页**；螺旋桨与其他特殊部位按子部位每 **2 张一页**。
- **清洗报告**：剔除对比结果页与污损概览详细页。

**PDF 的版式就是报告页面的最终样子**——报告页面上的任何内容问题都会原样出现在 PDF 里；反过来，改报告页面的展示样式也会直接改变 PDF。

在线预览模式额外有工具栏：列表 / 网格视图切换、`Ctrl/Cmd + 滚轮` 缩放，**缩放范围 0.3 – 2.5，步长 0.1**。

### 2.11 客户、船队与船舶授权

> **本章小结**：这里维护客户主体、客户侧 App 账号，以及「这个客户能看到哪些船」；界面上的「客户」在系统里其实叫船队，是新人最容易被绕晕的一处命名错位。

#### 做什么
「AM 配置中心 → 客户配置」维护客户主体、客户侧 App 账号，以及「这个客户能看到哪些船」。

#### 给谁用
AM（只看自己是主/辅 AM 的客户）、AM 管理员、管理员（看全部）。

#### 先分清三个词

| 界面叫法 | 系统里其实是 | 说明 |
|---|---|---|
| **客户** | 一条「船队组织」记录 + 船队扩展信息 | 能力层叫 fleet（船队），UI 层叫「客户」 |
| **客户成员** | 一个用户账号 + 客户扩展关联 | 客户侧的 App 登录账号 |
| **组织** | 组织的全集（含纳百自己） | 分两类：纳百组织、船队组织 |

⚠️ 同一份数据在接口里叫「船队 ID / 船队名」，在界面上写「客户名称」。**这是新人最容易被绕晕的一处命名错位。**

#### 客户（船队）主数据

- 字段：中文名、英文名、状态（正常 / 禁用）、主 AM、辅 AM 列表、logo、飞书主体。
- 中英文名**双向查重**，重复直接报错。
- 主 AM 的默认值规则：显式指定则用指定值；创建者是 AM 则设为自己；创建者是管理员 / AM 管理员则设为「通用 AM」。
- 主辅 AM 修改的三条硬规则（提示原文）：
  - `普通AM不能修改主AM`
  - `只有主AM才能修改辅AM`
  - `用户不能既是辅AM又是主AM`
- 一个组织的主 AM 数量有上限。
- ⚠️ 前端主/辅 AM 改动即时保存，**失败时静默重拉、没有任何错误提示**。

#### 客户成员（App 账号）

创建规则：

- 必填：用户名、邮箱、密码。**邮箱同时就是登录账号**，全局唯一。
- 邮箱格式错误提示 `邮箱格式错误`；邮箱重复提示 `邮箱已存在`；用户名重复提示 `客户名称已存在`。
- 密码必须是 MD5（前端加密后传）。
- 角色固定为「客户」，**允许登录的平台固定为客户 App**——客户账号进不了运营后台。
- 手机号校验用国际号码库，默认国家 CN，失败提示原文 `请输入有效的手机号码（支持国际格式，如 +86 138 0000 0000）`。⚠️ **后端的手机号校验被注释掉了。**

两个成员级开关（列表上直接下拉切换，500 毫秒防抖）：

- **客户管理员**
- **是否具有清洗决策权**——决定这个成员能不能在 App 上点「确认清洗」

（文案 `客户管理员状态更新成功` / `清洗决策权状态更新成功`）

启用/禁用成员**必须填原因**，弹窗标题 `请确认是否<启用|禁用>该用户`、必填提示 `请填写原因`。禁用/删除时会在缓存里打一个「账号失效」标记，客户 App 侧的鉴权每次请求都读这个标记、**即时把人踢下线**（标记保留 7 天）。

⚠️ 成员列表固定拉 100 条，**超过 100 个成员会被静默截断**。

#### 删除客户成员（带预检）

同一个能力两用：不传转移目标 = 预检；传了 = 执行转移并删除。

规则顺序：

1. **同一客户下只剩一个账号时不允许删除**，提示原文 `该客户下只有一个账号，不允许删除`。
2. 这个人名下有出动订单时，返回「需要转移」+ 可选转移目标列表（排除自己和已删用户）。
3. 执行时三条校验，文案原文：`转移目标用户不存在` / `转移目标用户不属于同一客户主体` / `不能将订单转移给自己`。
4. 转移完成后删除成员并打失效标记。

前端转移弹窗标题 `删除成员`，确认按钮 `确认删除`（危险样式），正文 `该用户有 N 个 mobi 订单，请选择订单转移目标：`；未选目标提示 `请选择订单转移目标`。

#### 船舶授权：两层，别搞混

| 层 | 语义 | 覆盖方式 |
|---|---|---|
| **客户主体授权** | 这个客户总共能看到哪些船（船池上限） | **全量覆盖**——加一条船也是把完整列表整体提交一次 |
| **成员授权** | 某个成员在客户船池内被授权的子集 | 受客户主体授权约束：**船不在客户船池里就授权不了** |

- 客户主体授权列表返回：船舶 ID、IMO、MMSI、中英文名、船型、是否年度计划、是否船漆保障。
- 成员授权列表只返回船舶 ID、IMO、中英文名（**没有 MMSI 和计划标记**）。
- ⚠️ 客户主体授权列表的模糊搜索是**在内存里过滤的**（先拉全量再筛），不是数据库分页。
- 客户侧越权防护：客户自己创建出动时会校验角色和船舶归属。

客户成员行点开的抽屉里有三个页签：船舶权限、出动权限、用户信息修改。

- 列表支持按 IMO 前缀、船名模糊、船型、是否年度计划、是否船漆保障筛选，默认按创建时间倒序。

- 船名脱敏逻辑代码里有但被关掉了，注释写「暂时取消脱敏操作, 增加权限后再增加」。

### 2.13 AM、调度与作业资源主数据

> **本章小结**：内部员工账号统一在「用户管理」里建，靠打角色区分身份；港口/大区/区域是三个不同的东西；工作船、潜水公司、作业队各有各的缺口。

#### 员工账号统一入口

所有内部角色都是用户表里的一行，在「管理员权限 → 用户管理」维护：姓名、登录账号、密码、操作平台、角色（多选）、组织、飞书 ID。**角色下拉里过滤掉了「客户」**——客户账号必须走客户配置创建。

#### AM

- AM 与组织的关联带类型：**主 AM / 跟单 AM（辅 AM）**。
- 两个列表能力：全量 AM 列表、按客户查 AM。返回字段：AM ID、用户名、账号、邮箱、手机、状态（按客户查时多返回组织中英文名）。
- ⚠️ 旧的主 AM 记录是软删的，下游查询必须过滤软删标记，否则旧 AM 还会出现在列表里（飞书缺陷 6981856549，已在提醒邮件侧修复）。

#### 调度

- 列表只返回调度 ID 和用户名两个字段。
- ⚠️ **只返回「调度」角色，不含「调度管理员」。**

#### 调度区域

把调度员绑定到一批区域，决定其可见 / 可派的作业范围。**删除是按调度员整体删，不是按单条区域删。** 前端必填提示 `请选择调度` / `请选择区域`，成功 `调度区域添加成功`。

#### 港口 / 大区 / 区域——三个不同的东西

| | 港口 | 大区 | 区域 |
|---|---|---|---|
| 是什么 | 具体港口 / 泊位 | 业务大区（如 SG） | 行政区划树 |
| 层级 | 平级 | 扁平 | 树形：国家 / 省份 / 城市 |
| 可维护 | ✅ 增删改查 | ❌ 只读 | ❌ 只读 |

**港口同时挂在行政区划和业务大区两条线上，两者独立且都必填。** 大区代码用于生成作业群编号（见 2.18）。

港口字段与校验文案原文：`港口名称不能为空`（中英文名共用同一句）、`区域不能为空`、`大区不能为空`、`港口类型不能为空`、`港口ID不能为空`。可选字段：港口代码、二级港区中英文名、所属航线、是否清水、经纬度、备注。港口类型两种：码头 / 锚地。

#### 工作船

- 字段：IMO、MMSI、中英文名、船长、船宽、**工作船属性**（长租船 / 短租船）、**工作船类型**（单机模式 / 双机模式）、备注、遥控箱列表。
- **没有删除能力。** 状态里有「暂停使用」，但**没有任何入口能把它改成暂停使用**（创建时固定写「生效中」）。
- 遥控箱唯一性校验（一个遥控箱只能绑一条工作船），错误文案模板 `%s已经被工作船%s添加`（同次提交内重复）、`%s已经被%s添加`（已被别的工作船占用）。
- 前端必填：中文名、英文名、工作船属性、工作船类型；IMO / MMSI / 船长 / 船宽可选。⚠️ **新增弹窗里的遥控箱字段被注释掉了，只有编辑抽屉能配遥控箱。**

#### 潜水公司

只有 ID、中文名、英文名三个字段，**运营后台没有维护页面**，只在作业相关页面作为下拉选项出现；数据只能直接改库。

#### 作业队

队长和队员两个列表，字段是 ID、用户名、账号（**队长列表不返回账号**）。不在后台单独维护，靠「用户管理」给账号打角色。

### 2.14 设备台账与防拆开盖记录

> **本章小结**：设备不是手工录入的，是开机上报时自动注册的；台账里能改的只有一个开关；防拆告警固定发到一个飞书群。

#### 做什么
「设备管理」页维护机器人、遥控箱等设备的台账，查看防拆开盖记录，出问题时远程禁用设备。

#### 给谁用
管理员、设备运维。

#### 关键认知：设备不是手工录入的

**没有「新增设备」的入口。** 设备是在开机上报时自动注册进台账的——第一次上报某个序列号，系统就插一条记录、状态置正常、注册时间用上报时间。触发点是遥控箱开机上报、机器人开机上报、网关开机上报。

#### 字段与枚举

台账字段：型号（**硬编码为 Magneto**）、设备类型、设备序列号、设备状态、是否开启防拆监控、开盖模块、开盖地点、开盖时间、禁用时间、禁用原因、注册时间。

- 设备状态：正常 / 禁用。
- 设备 / 模块类型共 **22 个有效值**：机器人、机器人-主控盒、机器人-电源盒、机器人-Fog 盒、机器人-泵压盒、机器人-顶出盒、遥控箱、遥控箱门、遥控箱前门、遥控箱后门、遥控箱-AIS、遥控器、线缆等。其中只有「设备级」类型（机器人 / 遥控箱 / 遥控器 / 线缆）会进台账。
- ⚠️ **前端筛选下拉是硬编码子集**，不是全量枚举：设备类型只有「机器人」「遥控箱」两项；开盖模块只有主控盒、电源盒、顶出盒、遥控箱门四项。

#### 启用 / 禁用规则

- 禁用**必须填原因**；启用也记原因和时间。
- **已是禁用态再点禁用会报参数错误**（反之亦然）——不是幂等操作。
- 列表的状态列鼠标悬停可看禁用时间和原因。
- 启用原因和启用时间**落库了但列表不返回**。

#### 编辑设备

⚠️ **抽屉里的「编辑」只能改一个字段：是否开启防拆监控。** 成功提示 `更新成功`；取消编辑的二次确认标题 `确认不保存?`、内容 `确定则关闭页面, 当前修改不做保存`。

#### 防拆开盖记录从哪来

链路：遥控箱检测到开盖 → 上报网关 → 网关上报云端 → 落库 → 发飞书告警。

1. 遥控箱通过消息上报开盖事件。
2. **没有 GPS 定位时先缓存起来，等拿到 GPS 后补发**（缓存保留一个月）。
3. 云端落库时调用地图服务做逆地理编码拿地点名；失败只告警不阻断。
4. 主记录存一条事件，明细按模块各存一行。
5. 最后发飞书告警，失败只告警不回滚。

台账列表只展示**最新一条**开盖记录。地点名取不到时降级显示「经度,纬度」；开盖时间取不到时降级用网关上报时间。

#### 飞书告警发给谁

⚠️ **告警不区分收件人、不可配置**——全部进同一个固定的飞书群（群机器人地址硬编码在代码里）。

卡片文案模板：

- 标题：`「Magneto」「<设备类型>」 - 「<序列号>」`，橙色卡头
- 正文：`在「<地点>」，「<模块列表>」被拆开，上报时间<时间>`（时间格式 `Y-m-d H:i`；模块列表用顿号拼接，**末尾会多一个顿号**）
- 按钮：「立即禁用」，⚠️ **跳转地址是硬编码的内网地址，外网点击无效**

#### 遥控箱

- 运营后台对遥控箱唯一的「管理」动作是**给工作船绑定遥控箱**（列表只返回 ID 和序列号）。
- ⚠️ 有一个名字里带 "poweron" 的设备侧能力**不是「远程开机」，而是设备侧的「上报遥控箱开机信息」**。整个后端**没有远程开机 / 下电的 HTTP 能力**；对遥控箱的下行控制走消息通道。

#### 前端页面存在但接口零引用的情况（如实说明）

运营后台的接口客户端是由后端接口描述整体生成的，所以里面有很多**属于边缘侧 / 设备侧、后台根本不该调**的能力。经核对，以下在前端零引用：设备开机上报、机器人上报、OTA 文件上传、数据文件上传、船体分区创建/编辑、批量船舶授权、手动触发提醒邮件、海生物删除。其中「设备台账 UI 该归运营后台还是独立的设备管理平台」见第 5 章待确认。

### 2.15 海生物配置

> **本章小结**：这个页面维护的清单**不影响报告里能选哪些海生物**——两套数据源完全不通，是全后台最容易误判的一处。

#### 做什么
「AM 配置中心 → 海生物配置」维护一份海生物类型清单，每项带中英文名和一对显示颜色（背景色 + 字体色）。

#### 给谁用
凡能进 AM 配置中心的账号都能增改（**这个页面的能力层没有任何角色校验**，可见性靠菜单控制）。

#### 业务规则

- 四个字段全必填：海生物中文名、英文名、背景颜色、字体颜色；两个颜色必须是合法十六进制色值。
- 四字段联合查重，重复报「数据已存在」。
- 列表默认按创建时间倒序。
- 前端文案：标题 `海生物配置管理`、按钮 `新增海生物配置`；必填提示 `请输入海生物中文名称` / `请输入海生物英文名称` / `请输入背景颜色` / `请输入字体颜色`；占位 `请输入背景颜色，如：#FFFFFF`。
- **页面上没有删除按钮**（删除能力存在但前端零引用）。

#### ⚠️ 关键限制：它**不影响**报告里可选的海生物类型

这是新人和运营人员最容易误判的一处。报告里能选哪些海生物，来自 helix 侧的**一份硬编码清单**（见 2.8 末），与这张配置表**没有任何代码引用关系**（全仓检索确认）。所以在这个页面新增一种海生物，报告页的下拉里**不会出现**。**团队早期的口径是「类型清单可在后台『海生物配置』里维护」，但代码上这张表与报告链路零引用**，两者存在冲突，见第 5 章待确认。

系统里实际存在**三套**海生物类型清单：① 后台这张配置表；② 报告用的硬编码 8 类；③ 老出动评级用的硬编码 11 类。

⚠️ 另有两处已知缺陷会直接影响运营人员操作：新建时**两个颜色字段会被丢弃、不入库**（必须再走一次编辑才生效）；列表页「中文名」列绑的是英文名、「英文名」列绑的是中文名，**标题与数据交叉错位**。

### 2.16 定期提醒邮件

> **本章小结**：按客户配置「哪些船、发给谁、隔多久提醒一次」，由定时任务发出；⚠️ 每保存一次配置，该配置下的退订记录会被清空。

#### 做什么
按客户配置一条规则：「哪些船、发给哪些客户成员、隔多久提醒一次」，系统定时给客户发一封提醒邮件（提醒该做检测/清洗了）。

#### 给谁用
AM 在「AM 配置中心 → 定期提醒邮件」配置；邮件收件人是客户侧的成员账号。

#### 配置项

| 字段 | 必填 | 限制 |
|---|---|---|
| 客户 | ✅ | 提示 `请选择客户` |
| 配置成员账号 | ✅ | 提示 `请选择配置成员账号`；**收件人就是这些成员的邮箱** |
| 船舶类型和船名 | ✅ | 提示 `请选择船舶类型和船名`；未选客户时禁用 |
| 提醒周期（单位月） | ✅ | **最小 0.5，步长 0.5，1 位小数** |
| 邮件间隔周期（单位天） | ✅ | **最小 1，步长 1，整数** |
| 年度订单专属提醒 | | 开关，说明文字原文「仅对购买年度订单的船舶进行提醒」 |

#### 业务规则

- **同一个客户下，一条船只能被一条提醒规则配置**，冲突提示原文 `%s已经配置了提醒，不能再次配置`（船名英文优先）。
- 删除是软删。
- **发送判定**：
  - 只有**已结束且未取消**的出动才纳入统计（飞书缺陷 6996709358）。
  - 基准时间取实际抵达时间，取不到时降级用 ETB。
  - **距今月数 > 提醒周期**才够格；⚠️ **一个月按固定 30 天算。**
  - 10 分钟内已有「发送中」记录 → 跳过（防并发重发）。
  - 最近一次成功发送距今**不足「邮件间隔周期」天数** → 跳过。
- **船舶可见范围**：管理员 / 调度管理员看全部；AM 看本组织授权的船；客户管理员看本组织授权的船，普通客户成员只看自己被授权的船。**船舶标识解析失败按拒绝处理**（防越权，飞书缺陷 6981903028）。
- 年度订单开关打开时只含年度订单船；关闭时含全部（年度船仍展示年度订单卡片）。
- 已退订的用户跳过。

#### 定时任务的执行细节

- **邮件主题固定为 `Neptune Reminder`**，不可配置，不含客户名或船名。
- 每页 **10 条**分页循环处理，直到取完。
- 支持**广播分片**：多个执行器实例按规则标识哈希分片，各处理自己那一份，互不重复。
- **按人精确投递**：老实现会给同一份配置的所有成员各发一遍，导致 N 封重复邮件；现已改为按人投递（飞书缺陷 6981842633）。
- 用乐观锁防并发：版本冲突时跳过本次。
- 收件人邮箱为空的成员直接跳过、不发也不写状态。
- 邮件正文由公共渲染服务生成 HTML，再由后端走 SMTP 发出（《产品线依赖地图》§2.5）。
- **执行周期不在代码里，在调度中心控制台配置。**

#### 退订

- 邮件里的退订链接带一个签名，**有效期 30 天**。
- 退订是「规则 + 人」维度的：退订某条配置不影响其他配置。
- ⚠️ **每次保存提醒配置都会把退订记录清空**——AM 编辑一次配置，此前所有客户的退订就失效了。这是需要在流程上规避的一条（见第 5 章）。

#### 客户 logo

- 上传入口在**客户配置的基本信息页签**，不在提醒邮件页。
- 限制：必须是图片、**≤ 5 MB**（提示 `请选择图片文件！` / `图片文件大小不能超过5MB！`）。
- 存到该组织的 logo 目录下，同时写回组织记录。
- 成功 `LOGO上传成功`，失败 `LOGO上传失败`。

⚠️ 「成员是否有该船权限」的校验在保存提醒配置时**被整段注释掉了**（飞书缺陷 6979325220 的修复已失效），逻辑本身还在，文案是 `%s 账号不具有 %s 船的权限`。

⚠️ 产品需求文档里写的默认值（4.5 月 / 14 天）**代码里没有实现**，新建表单没有默认值。

### 2.17 年度订单与消耗

> **本章小结**：为客户维护六种年度额度并记录消耗；扣额度有三级优先级；⚠️ 每次编辑订单会清空消耗历史。

#### 做什么
「AM 配置中心 → 年度订单设置」为客户维护年度服务额度，并记录每次作业消耗了多少额度。

#### 给谁用
AM、AM 管理员、管理员。新建订单时会自动授权给该组织的**全部活跃 AM**（管理员创建也一样，否则 AM 看不到自己客户的订单，飞书缺陷 6980660712）。

#### 六种额度

| 代码 | 含义 |
|---|---|
| VS | 侧板清洗额度 |
| FB | 底板清洗额度 |
| PP | 螺旋桨抛光额度 |
| Niche | 特殊部位清洗额度 |
| UWI | 常规检测额度 |
| AMSA UWI | 澳新标准检测额度 |

⚠️ **前端目前只允许编辑 FB 一项，其余五项全部禁用。** 输入步长 0.1、1 位小数，默认全 0。过期时间默认 **当前 + 365 天**。

#### 额度怎么扣：三级优先级

每个订单有两个池：**独享额度**（本订单自己的）和**共享额度**（贡献到客户级共享池的）。扣减时按以下顺序找额度：

1. 本订单的独享剩余；
2. 同客户、且包含同一条船的其他订单的独享剩余，按过期时间从早到晚；
3. 同客户**全部订单**的共享剩余，同样按过期时间从早到晚。

三级都不够 → 报错。**超额提示会指出具体缺哪一项缺多少**，格式 `额度不足: VS 缺 1.5, FB 缺 2`（字段顺序固定 VS, FB, PP, Niche, UWI, AMSA-UWI）；定位不到具体项时才返回笼统的 `额度不足`（飞书缺陷 6928975534）。

每次扣减写一条消耗记录，独享和共享**分开记两条**。系统会自动生成备注，模板原文 `%s被%s共享消耗%v`（例如 `FB被MV XXX共享消耗2`），多段用 `; ` 连接。

**订单耗尽（独享和共享剩余都 ≤ 0）后会从列表消失。**

#### 校验

- 创建/编辑：客户必填（`org_id is required`）、船舶必填（`vessel is required`）。
- 消耗：订单号、船舶、客户、额度四项都必填。
- 非全权用户操作看不到的订单 → 无权限。
- 新增、消耗、删除三类动作**同一次请求只能有一类**，否则报 `count must be 1`。
- 用乐观锁防并发覆盖。

⚠️ **每次编辑年度订单都会把消耗历史清空**——这是需要在流程上规避的一条（见第 5 章）。

#### 「年度订单补充信息」是另一回事

helix 侧还有一份「年度订单补充信息」，**它不是订单额度，是出动维度的年度计划船况档案**：上次干船坞日期、上次船体清洗日期（非纳百）、上次船体检测日期（非纳百）、最后一次螺旋桨抛光日期、侧板/底板油漆类型、左右海底门与应急海底门（高 / 低 / 高+低 三态 + 数量）、螺旋桨页数、其他海底门、特殊工况。它在新建出动的「补充信息（非必填项）」折叠区里填，会被提醒邮件与年度订单卡片读取。

### 2.18 飞书作业群自动建群

> **本章小结**：推进到「作业安排」时系统自动建飞书群，按作业地点逐级累加拉人；群名有一套完整的编号规则，且有人手动改过群名后系统就不再覆盖。

#### 做什么
新出动推进到「作业安排」时，系统自动建一个飞书群，按配置把相关人和机器人拉进去，并在群里推一张作业情况卡片。

#### 给谁用
调度与调度管理员（手动建群只有这两个角色能点）；「作业群默认拉人配置」在「调度配置中心」维护，**只有管理员或调度管理员能增删改**。

#### 默认拉人配置的维度是**作业地点**，不是客户

配置一条规则 = 「一批作业地点」+「一批成员（人 + 机器人）」。作业地点有 5 级：国家 / 大区 / 城市 / 港口 / 全部。

**匹配是「从精确到宽泛逐级累加去重」，不是命中一条就停**：港口 → 大区 → 城市 → 国家 → 全部。也就是说，新加坡某港口的一次出动，会同时拉到「该港口」「新加坡大区」「新加坡」「全部」四条规则里配的人。

前端细节：

- 弹窗标题「人员配置」，两个必填项：`请选择角色`、`请选择作业地点`。
- **规则名是前端自动生成的（所选成员名用顿号拼接），用户不能自己填。**
- 成员下拉把「人」和「机器人」混在同一个多选框里。
- 作业地点级联选项 = 「全部」+「国家→城市」+「大区→港口」，构建时会**过滤掉名称含「待定」的节点**；无港口的大区被过滤掉；大区标签形如 `新加坡（大区）`。
- 成功 `配置添加成功`。

⚠️ 「同一用户不能被配到多条规则」的校验**是死代码、全仓无调用**——所以同一个人可以被配到多条规则里（文案 `用户 %s 已在配置 [%s] 中，无法重复分配`）。

#### 群名规则

群名格式：**`[行动编号]船名 日/月 港口名 二级港口名 (出动UID)`**
行动编号格式：**`大区代码_序列号+后缀_年份`**

示例：`[SG_0001D_2025]MV XXX 12/3 Singapore Jurong (A1B2)`

各段规则：

- 船名取不到时降级 `Unknown Vessel`；港口名取不到时降级 `Unknown Port`；大区代码取不到时降级 `UNKNOWN`。
- 日/月基于**预计抵达时间**。
- 港口名默认用英文；**只有国家是「中国」时才用中文名**。
- **潜水员后缀**：纯潜水员作业 → `QS`；潜水员 + 其他方式 → `D`；无潜水员 → 无后缀。
- 序列号 4 位（如 `0001`）；**大区没变就复用已有序列号，大区变了或格式非法才重新生成**。
- 出动 UID 是 4 位随机码，字符集 34 个字符（**去掉了容易混淆的 O 和 I**），组合数 34⁴ = 13,366,336，最多重试 15 次。
- **群名长度上限 60 字符**；超长时取前 57 个字符作群名，剩余部分加上默认描述作为群描述。群默认描述常量：`自动创建的MOBI作业群`。

#### 触发时机：两条路径

**A. 自动 —— 出动状态流转到「作业安排」时**

1. 先检查作业安排是否就绪；
2. 已有群则跳过；
3. 加一把 **60 秒**分布式锁，锁被占用提示 `建群中，请稍后重试`；**缓存异常时不阻塞，继续建群**（靠飞书幂等 + 数据库唯一约束兜底）；
4. **如果执行方式只有「潜水员」一项，则只生成行动编号、不建群**；
5. 建群失败时异步发飞书通知。

**B. 手动 —— 点「创建飞书群」按钮**

校验链与提示文案原文：

- 未取到用户 → `未获取到用户信息`
- 角色不是调度或调度管理员 → **`只有调度或调度管理员可以创建飞书群`**
- 出动不存在 → `查询出动任务失败`
- 状态不在「作业安排」及之后到「已完成」之间 → **`只能在作业安排及之后创建飞书群，当前状态: %s`**
- 已有群 → **`该出动任务已创建飞书群，创建飞书群失败`**
- 锁被占用 → `建群中，请稍后重试`

#### 群成员来源

两部分汇总：

1. 该出动所属客户的**主 AM 和辅 AM**；
2. 按作业地点 5 级匹配到的配置成员。

**没有配置就不加人、不加机器人**，不会回退到配置文件里的默认值。

建群有降级链：优先用第一个成员做群主建外部群，失败则逐个候选人单人建群再补拉成员；成员分批添加。

#### 收尾动作

1. 回写群 ID、行动编号，并把「群名自动更新」开关置为允许。**回写失败不回滚**，会异步发告警要求手动补录：`飞书群已创建成功，但数据库更新失败，需手动补录。群ID: %s, 行动编号: %s, 错误: %v`。
2. **异步**加机器人。机器人加入失败**只记日志、不重试、不报错**。
3. **异步**在群里发作业情况卡片。

#### 群名自动更新开关

- 建群时默认「允许」。开着的时候，出动信息变了（日期、船名、港口、执行方式）系统会自动刷新群名，但序列号沿用。
- **只要有人在飞书里手动改过群名，系统就自动把这个开关关掉**，之后不再覆盖用户的命名，并在群里发一条提示。日志原文：`用户 %s 修改群名: 「%s」→「%s」，已禁用出动 %d 的自动更新群名`。

### 2.19 新加坡展会获客

> **本章小结**：展会前发 VIP 邀请函、现场收留资、展后发建联邮件；权限不走系统角色而是配置文件白名单，是本后台唯一带免登录公开接口的模块。

> **归属存疑**：后端已独立成一个服务，前端挂在运营后台里，且是本后台唯一带免登录公开页的模块。是否该独立成第五条产品线，见第 5 章待确认。

#### 做什么
展会前发 VIP 邀请函、展会现场收集意向客户留资、展后发建联邮件。

#### 给谁用
BD 和 AM。⚠️ **权限不走系统角色，而是配置文件里的用户白名单**：

| 能力 | BD | AM | 其他登录用户 |
|---|---|---|---|
| 查看意向客户列表 | ✅ | ✅ | ❌ `无查看权限` |
| 审核意向客户（通过/拒绝） | ✅ | ❌ `无审核权限` | ❌ |
| 发建联邮件 | ✅ | ✅ | ❌ `无发送权限` |
| 查看 VIP 列表 | ✅ | ✅ | ❌ |
| 读写常见问题库 | ✅ | ✅ | ✅（**无门禁**） |

⚠️ 运维含义：**新增一个 BD/AM 要同时改两处配置（角色白名单 + 邮件签名）并重启服务**，没有热加载。漏配角色白名单会导致所有人都是「无查看权限」。签名配置里含发件邮箱和密码。

展会菜单**不在任何角色白名单里**，所以在动态菜单下只有管理员和 AM 管理员能看到展会菜单。

#### VIP 客户页

只读列表，4 列：客户姓名、公司、邮箱、提交时间；默认每页 20 条；**没有任何操作按钮**。

#### 意向客户页

- 列：留资时间、客户名、客户姓、邮箱、电话、公司/组织、职务、与航运相关的公司类型。
- **「私人活动操作」列仅 BD 可见**：待审核状态显示「通过」「拒绝」，确认文案 `是否确认邀请客户？` / `是否确认拒绝客户？`，成功提示 `已通过` / `已拒绝`；状态三档：待审核 / 已通过 / 已拒绝。
- 「建联邮件操作」列：已发送则显示 `已发送（发送人）`，否则显示「发送建联邮件」。
- 搜索框按邮箱查，防抖 300 毫秒；另有「常见问题库」「添加常见问题」两个按钮。
- 发建联邮件前会校验发件人签名：未配签名 → `当前用户未配置签名信息，请联系管理员`；未配邮箱 → `当前用户未配置邮箱，请联系管理员`。建联邮件有 3 种模板变体。
- 审核校验文案：`无效的客户ID`、`审核状态只能是1（通过）或2（拒绝）`。

#### 免登录公开页

后端确实有三组免鉴权的公开能力（邮箱验证码、邀请函确认/拒绝、留资提交），注册在鉴权中间件之前。

前端两个页面：

- **现场登记页**：现场签到名单，右上角显示「已核销/总数」。⚠️ 它调的后端能力在整个后端**不存在**（地址也指向了错误的服务），**当前应为未接通状态**。
- **扫码页**：⚠️ **已停用**，整页返回空；原实现和对应后端能力都已注释。

⚠️ 两个页面虽然挂在登录布局之外，但前端全局仍会把未登录用户重定向到登录页——**所以严格说前端是有鉴权的，只有后端能力无鉴权**。

#### 后端还有哪些能力

- **邀请函**：Excel 批量导入 VIP 名单 → 生成 H5 邀请函 + 二维码（存对象存储的展会目录）→ 批量生成确认链接 → VIP 点确认/拒绝 → 现场扫码核销。
- **意向客户**：邮箱验证码（带发送间隔限流）→ 留资提交 → BD 审核 → 通过后自动发邀请邮件。另有一套「平板五步漏斗」：提交留资 → 提交动机 → 完成游戏 → 确认信息 → 领礼品。
- **礼品库存**：两种礼品（3D 挂件 / 行李牌），**按 2:1 比例分配**——每 3 轮里前 2 轮发 3D 挂件、第 3 轮发行李牌；扣减是原子操作，某种缺货时自动降级到另一种，都没了报「全部礼品已发完」。
- **计数器**：为礼品分配提供全局单调递增的轮次号，是 2:1 配比的唯一依据。
- **常见问题库**：问题 + 答案，可作为建联邮件的选填内容带出。

#### 邮件模板

在公共渲染服务里，共 5 套：

| 模板 | 用途 |
|---|---|
| VIP 邀请函 | 含参加 / 谢绝两个操作链接 |
| 意向客户邀请函 | 审核通过后发 |
| 建联邮件 | 含 AM 签名与常见问答，3 种变体 |
| 邮箱验证码 | — |
| 定期提醒邮件 | 非展会用；只有组件、没有独立入口 |

⚠️ **VIP 邀请函模板有两处未完成**：生产环境的落地页地址指向的是开发机内网 IP，图片地址全是占位符——线上发出去的 VIP 邀请函按钮与图片都会失效。

## 3. 与其他产品线的接口

> **本章小结**：运营后台向上承接边缘侧采集的数据，向下是客户 App 全部内容的唯一来源；本后台前端没有任何实时通道，全靠轮询。完整依赖矩阵见《产品线依赖地图》。

### 3.1 运营后台 ← 边缘侧（NOS / BOS）

| 运营人员感知到的现象 | 背后是什么 |
|---|---|
| 报告页里出现照片 | 边缘侧打包上传对象存储 → 云端抽帧 + AI → 入库（2.7） |
| 部位照片计数在变 | 云端抽帧完成后回传计数给地面站 |
| 现场刚拍的照片后台还看不到 | 边缘网络不稳时会排队续传——报告页照片不全时**先确认是否还在上传中** |
| 清洗策略页的三板档位 | 边缘 AI 算出污损网格与推荐档位，云端可下发档位到地面站 |

**运营后台前端没有实时通道**（无消息推送、无长连接），所有异步任务（照片打包等）都是**轮询**（《产品线依赖地图》§2.6）。

### 3.2 运营后台 → 客户 App

运营后台是客户 App 全部内容的**唯一数据来源**，但两者是**两套账号体系、两个入口**（《产品线依赖地图》§2.8）：

| | 运营后台 | 客户 App |
|---|---|---|
| 谁用 | 内部员工 | 船东 / 船舶管理公司 |
| 账号 | 用户管理页创建 | 客户配置页创建（**只能登 App**） |
| 联动 | 后台禁用/删除客户账号 → 打失效标记 → App 端**即时**被拦下线 | |

运营人员的动作如何影响客户看到什么：

- 检测报告审核时选了「建议客户洗船」→ 客户 App 才会出现「确认清洗」按钮。**客户反馈看不到按钮时先查这里**。
- 新建出动时勾了「是否需要在 APP 展示」→ 决定这次出动在 App 上可见与否。
- 客户成员的「是否具有清洗决策权」开关 → 决定这个成员能不能点确认清洗。
- 清洗报告发布 → PDF 生成 → 顺带写一条「最终报告」文件记录 → App 端最终报告节点才能流转（2.10）。
- 客户在 App 上点「确认清洗」是**客户唯一的回写动作**，流程才进入清洗阶段。

### 3.3 运营后台 → 公共渲染服务

三种用法（《产品线依赖地图》§2.5）：

1. **报告预览**：页面里内嵌报告页。
2. **PDF**：定时任务用无头浏览器打开报告页截图（2.10）。
3. **邮件正文**：提醒邮件、展会各类邮件的 HTML 都由它渲染，后端只负责取回 HTML 并发送。

渲染服务**自己不落库、不发邮件、不上传对象存储、不决定收件人**——它是纯渲染器。所以「邮件发错人」「PDF 没生成」这类问题都不在它那一侧。

### 3.4 运营后台 → 飞书

飞书是内部消息通道：新出动自动建作业群（2.18）、设备防拆开盖告警（2.14）、照片打包下载链接推给主/辅 AM（2.7）、出动流程阶段卡片与审批卡片（2.2）、服务出错告警。

⚠️ 出动流程的「预览报告 → 清洗中」这一步**必须走飞书审批卡片闭环**，界面上不提供手动入口，为的是审计可追溯。

### 3.5 上传文件的方式

运营人员在后台上传的照片、审批文件、最终报告、船图，都是**浏览器直传对象存储**：先向后端换一个临时上传凭证，再由浏览器直接传上去，上传完成由对象存储回调后端登记。所以上传大文件不会经过后端服务器，但**上传失败的排查要看浏览器网络面板而不是后端日志**。

## 4. 关键业务流程（端到端）

> **本章小结**：以最典型的「先检后洗」为例，逐环节写清「谁在哪个页面做什么、卡住了看哪里」。

### 第 1 步 建单（AM，作业设置）

AM 在「作业设置」点新增，填：下单人、跟单客服、船名、作业地点、ETB、是否在 APP 展示、出动任务（哪些部位、检测还是清洗）、执行方式、出动类型、作业标准。执行方式同时含游泳机器人和 N0/Magneto 时，还要选检测方案版本（10 线版 / 5 线版）。可在「补充信息」折叠区补录船况档案（上次干坞、油漆类型、海底门配置等）。
→ 出动进入「待开始」，流程面板按出动类型自动决定要出现哪些页签（2.2）。

### 第 2 步 作业许可（调度，审批文件页签）

调度上传海事备案（必填）、搭靠证、码头备案等审批文件。
→ 推进到「作业安排」。

### 第 3 步 作业安排（调度 + AM，作业安排页签）

安排潜水公司、潜水员预计抵达时间、工作船、遥控箱、作业队。**此时系统自动建飞书作业群**（按作业地点 5 级匹配拉人 + 主辅 AM + 机器人）；纯潜水员作业只生成行动编号、不建群（2.18）。
→ **卡住了看**：群没建出来查飞书告警通知；建群按钮点不动查角色（只有调度和调度管理员能点）。

### 第 4 步 抵达大船（AM，抵达大船页签）

船到泊位后回填实际抵达时间、吃水、水下能见度、水流。

### 第 5 步 现场检测（作业队，边缘侧）

作业队在船边作业平台上看到云端下发的出动列表，选中本次出动，框选作业区块，操控机器人沿检测线每米拍照。边缘 AI 实时判断照片是否合格并给出污损网格。数据自动上云。
→ **运营人员这一步在后台只需要做一件事：在「检测中」页签填「作业结束时间」。** 这个字段是后面报告能否发布/提交的硬前置条件（2.2）。
→ 后端对这一阶段有 **12 小时硬超时**，超时会推告警卡片到告警群但不改状态（2.2）。

### 第 6 步 检测报告（AM，检测报告页签）

数据齐了以后，AM 逐部位干四件事（2.3）：

1. 整理照片（检查自动归位结果、人工补传、挑选进报告的照片、打质量标记、开关水印）；
2. 核对/修正海生物与油漆标注（改的是等级的输入，系统重算等级，2.8）；
3. 写检测结论（海生物按 5 部位、油漆按 3 部位）和清洗建议（≤ 500 字）；
4. 逐部位审核通过（支持批量；批量时会检查照片数：默认特殊部位 6 张、其余特殊部位 2 张）。

发布时四道闸依次检查：数据是否异常 → 作业结束时间是否已填 → 清洗建议是否已填 → 是否所有部位都审核通过。
→ 审核通过时系统问「是否建议客户洗船」。
→ **卡住了看**：发布按钮灰着就把鼠标移上去看禁用原因，四种原因见 2.3。

### 第 7 步 客户决策（客户，App）

检测结果发布后推送到客户 App。选了「建议洗船」的，客户会看到清洗建议和「确认清洗」按钮。客户点确认，流程才进清洗阶段。
→ **卡住了看**：客户说看不到按钮，先查 AM 审核时有没有选「建议客户洗船」，再查这个客户成员有没有「清洗决策权」。

### 第 8 步 清洗作业（作业队，边缘侧）

出动进入清洗安排 → 抵达大船 → 清洗中。清洗完再做洗后检测拍照，数据同样自动上云。客户在 App 上能看到清洗进度。
→ 运营人员在「清洗中」页签填清洗作业结束时间，并**单独保存**「未清洗部位」（这个字段有独立的保存按钮，不保存就点完成会丢）。

### 第 9 步 清洗报告（报告组长 + 报告员，AI 报告管理）

1. **报告组长分配**：在「报告管理」列表把这单报告指派给某位报告员（可批量）。
2. **报告员制作**：在报告制作页逐部位整理照片组、核对海生物与油漆总览、上传/管理洗前视频、写 Attention（必填，≤ 500 字）。
3. **报告员提交审核**：系统逐条查 16 项门槛（2.5），任何一条不满足都提交不了，并明确告诉你缺什么。最常见的两条是「作业结束时间没填」和「照片没成组」。
4. **AM 审核**：AM 在流程面板「最终报告」页签的「清洗报告审核」子页点通过或驳回。

→ **卡住了看**：提交审核按钮灰着就看禁用原因文案；报告状态不对就看「操作记录」页查是谁改的。

### 第 10 步 出 PDF 与交付（系统自动 + 客户 App）

1. 审核通过 → 自动入队生成 PDF → 定时任务用无头浏览器打开报告页截图 → 存对象存储 → 回写下载地址；清洗报告额外补写一条「最终报告」文件记录（2.10）。
2. PDF 自动登记到流程面板「最终报告」环节。
3. 客户 App 出现「下载报告」入口，可下载、App 内预览、系统分享转发。
4. 报告里的照片可打包下载：小批量直下，大批量走异步打包（前端每 3 秒轮询、上限 30 分钟），完成后飞书把链接推给该客户的主/辅 AM（链接 180 天有效）。
5. 出动走到「已完成」（Temporal 侧这一步**必须客户账号确认结单**）。

### 全程可发生的旁路

- **暂停 / 恢复**：「作业安排」到「最终报告」之间可暂停，必填原因和描述；恢复也必填描述。
- **取消**：「待开始」到「最终报告」之间可取消，必填原因和描述，可勾选自动创建下一程出动。**取消不可恢复**，且会反向撤回已发的飞书通知卡片。
- **回退**：Temporal 侧非终态阶段都能由流程管理员逐级回退一节点，回退会重发飞书通知卡片（有意为之）。
- **报告冻结**：报告组长可冻结「未开始」「制作中」的报告，暂停一切流转；解冻后回到冻结前的状态。

### 排查任何问题的第一步

拿出动的 **Unique ID** 去各端对照——它是贯穿全系统的对齐钥匙。列表页 Unique ID 支持一键复制。

### A.7 易混淆点（运营人员必读）

1. **「检测报告」≠「清洗报告」**：前者是出动流程里 AM 的审核环节，后者是独立菜单里报告员的制作发布流程。沟通时务必说清指哪个。
2. **地址里的 `app` 不是客户 App**：那是运营后台自己的能力面，客户 App 走完全另一个入口（《产品线依赖地图》第 0 章）。
3. **R0–R4 是算出来的，不能直接改**：只能改标注（海生物种类 + 覆盖比例），系统重算。
4. **「刷新结论」带重建参数会清空所有人工编辑**——分区日志、审核状态、人工修正全丢。
5. **「作业结束时间」在「检测中」页签填，不在报告页里填**——报告提交/发布被拦，最常见就是这条。
6. **海生物配置页里加的海生物，报告里选不到**——两套数据源不通（2.15）。
7. **每次编辑年度订单会清空消耗历史；每次保存提醒配置会清空退订记录**——两条流程红线。
8. **冻结的报告谁都动不了**（报告组长的分配除外），解冻后自动回到冻结前状态。
9. **客户能不能看到「确认清洗」按钮**，取决于 AM 审核时是否选了「建议客户洗船」，以及该客户成员有没有清洗决策权。
10. **暂停/恢复失败时后台只说「请求参数错误」**——实际可能是原因非法、描述为空，或当前状态不允许（待开始/作业许可两阶段不允许暂停）。
11. **设备台账不能手工新增**，设备开机上报时自动注册；抽屉里的「编辑」只能改防拆监控开关一项。
12. **防拆告警发到固定的飞书群，收件人不可配置**；告警卡片里的「立即禁用」按钮是内网地址，外网点不开。
13. **报告页签集合有三层**：全局分区字典 → 某次出动的实际分区 → 某类报告的页签集合，改错层就改错人（2.9）。
14. **暂停和取消是两个独立状态**，不是流程节点；页签会截断到当前进度。
