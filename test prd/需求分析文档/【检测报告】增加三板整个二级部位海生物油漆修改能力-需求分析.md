## 一、需求概述

**一句话**：在**检测报告**环节，给**三板（左舷 / 右舷 / 底板）的每条检测线（line）**增加一种「整表式」的海生物/油漆类型及比例**批量修改**能力，交互复用**清洗报告表格整表修改**的模式。

**背景**：AM 经常需要修改较多的三板海生物/油漆情况，逐张照片标注效率低，故新增批量修改入口。

**需求概要原文**：
> 需求背景：当前因为 AM 需要修改较多的三板的海生物/油漆情况，需要一个批量修改的功能，故增加该能力。
> 需求明细：视觉稿待补充。增加类似清洗报告表格整表修改的功能，允许针对三板的每条 line 进行海生物/油漆类型及比例的整体调整，交互逻辑与清洗报告表格整表修改类似。

## 三、关联功能及业务逻辑

### 1. 检测报告环节（本需求落地处）
- 检测报告是**出动流程里 AM 的审核环节**（易与独立菜单的「清洗报告」混淆）。AM 逐部位核对照片与结论、审核发布。
- 现有单照片标注：每张照片可加**海生物记录（类型 + 覆盖百分比，最多 4 条）**、**油漆缺陷类型 + 覆盖档位**。现有的「批量标注」是**选多张照片**统一设置，与本需求的**按 line 整表修改**粒度不同。

### 2. 海生物 / 油漆的核心规则（改动直接牵动这些）
- **海生物类型硬编码 8 类**：贻贝、管虫、海草、海鞘、生物膜、海藻、藤壶（+「干净」，列表时跳过）；仅螺旋桨/艏侧推追加「钙沉积」。
  ⚠️ 这与后台「海生物配置」菜单维护的清单**不是同一份数据**，报告可选项不受配置页影响。
- **污损等级 R0–R4 是算出来的，无直接录入入口**：宏观覆盖率 >40%→R4，>15%→R3，有宏观→R2，仅微观→R1，无→R0。人工只能改「输入」（海生物种类 + 覆盖百分比），系统**重算等级**。
- **涂装 Good/Fair/Poor 用投票**，不是均值；单张按「缺陷等级 × 覆盖率档位」查表，段级/部位级投票取更差档。
- 改标注的机制是**追加「人工修正记录」**而非覆盖，读取时按顺序回放再算等级——批量改整条 line 需考虑这条回放链路。

### 3. 三板与 line
- 三板 = **左舷 / 右舷 / 底板**，每侧分 **L1–L10（10 条线版）或 L1–L5（5 条线版）**，每条线覆盖不同船体区域。

### 4. 检测结论
- 海生物结论按**五个部位**分别写、油漆结论按**三个部位**写；本需求新增的批量修改需与检测结论维护「手动改过则不同步」的分叉规则（评论 #6）。

### 5. 参考交互：清洗报告表格整表修改
- 需求明确「交互逻辑与清洗报告表格整表修改类似」。清洗报告与检测报告**共用同一套部位/照片/标注组件**，因此该整表修改组件可复用。
- ⚠️ 本地业务逻辑文档里**未检索到**「整表修改」的明确成文描述，如需精确对齐交互，建议打开 Figma 稿或清洗报告页核对。

## 五、机制链深挖与关键决策

一次「整表修改」会穿过三条现有机制链：

```
UI 整表修改（新）
   │  写入的是「算等级的输入」，不是等级本身
   ▼
人工修正记录（追加，非覆盖）  ←── 现有机制 ①
   │  读取时按顺序回放
   ▼
等级重算 R0–R4 / Good·Fair·Poor  ←── 现有机制 ②
   │
   ▼
检测结论 / 报告 PDF summary 表格  ←── 现有机制 ③（含手改 vs 同步）
```

### 机制 ① 人工修正记录（写回链路）
- 现状：双击照片卡编辑海生物标注时，系统**不是覆盖原数据，而是追加一条「人工修正记录」**（记录谁、改了哪张照片、哪个部位哪条线哪个位置、改成了什么）。读取报告时按顺序回放这些修正记录，得到最终数据再算等级。
- 海生物、油漆各有一套独立的人工修正记录（油漆在 `redo_writer.go`）。
- 打包下载前会先把人工修正记录应用一遍。
- 代码位置：`inspection.go:3251-3300`、`inspection_tools.go:1245-1251`、`redo_writer.go`、`media_download_task.go:203`。

**核心决策：写回粒度**

| 方案 | 语义 | 对现有机制的影响 |
|---|---|---|
| **A. line 级批量修正记录**（新增一类记录） | 一条记录作用域 = 某 line 全部照片 | 回放器要新增「按 line 展开」语义；打包/算等级都要先展开；与现有逐照片回放链路不同 |
| **B. 展开成逐照片修正记录** | UI 一次操作，后端对 line 下每张照片各追加一条 | 复用现有回放/算等级链路，但记录量爆炸，且「+5%」需按每张当前值分别换算 |

### 机制 ② 等级重算（只能改输入，不能改等级）
- **铁律**：全系统没有任何「直接录入污损等级」的入口，只能改「算等级的输入」，系统重算。
- 海生物 R0–R4 阈值：宏观 >40%→R4，>15%→R3，有宏观→R2，仅微观→R1，无→R0（`biofouling_assessment.go:42-86`）。
- 涂装 Good/Fair/Poor：投票，单张按「缺陷等级 × 覆盖率档位」查表，段级/部位级平票取更差档（2026 年 7 月替换旧均值算法）。
- **人工改过的段不会被自动重算覆盖**。
- 评论 #7/#8 印证：新功能 UI 只操作「类型 + 比例」，等级是重算产物，不可直接改。

### 机制 ③ 检测结论：手改 vs 同步
- 检测结论 8 个文本域（海生物结论 5 部位 + 油漆结论 3 部位），各上限 500 字。
- 现有「刷新结论」是**手动按钮 + 整体覆盖**；本需求要求的是**批量修改触发时自动判断是否同步**，需要一个「该部位结论是否被 AM 手改过」的**脏标记**。
- ⚠️ 红线：带重建参数的「刷新结论」会**先删整份报告文档再按默认值重建**，人工编辑全丢——整表修改必须与此隔离。

### 与现有「批量标注」的差异
| 维度 | 现有「批量标注」 | 本需求「整表修改」 |
|---|---|---|
| 粒度 | 选中多张照片统一设置 | 按 line（二级部位）整体调整 |
| 操作对象 | 照片集合 | 一条 line 的海生物/油漆类型及比例 |
| 交互 | 勾选照片 → 批量设置 | 整表（类清洗报告表格），± 步进 |

### 发现的一处文档口径冲突
`业务逻辑文档.md:499/508` 把油漆等级 Good/Fair/Poor 描述成「每个子区域独立下拉选择」（可录入）；而 `运营后台产品说明文档.md §2.8` 明确涂装等级是投票算出来的、无直接录入入口。与评论 #8 一致指向：**Good/Fair/Poor 是结果不是输入**，本需求应以「等级=投票产物、只改缺陷类型+占比」为准。

### 9.1 R0–R4 并存两套聚合口径（关键新发现，直接影响等级重算）

`产品线依赖地图.md` 明确：R0–R4 是算出来的、全仓库无「直接录入等级」接口，**但代码里并存两套聚合口径、明确「不可混用」**：

| 口径 | 算法 | 用途 |
|---|---|---|
| **部位级** | 先把该部位所有照片的覆盖比例**平均**，再套阈值评级 | 报告/部位结论 |
| **列表 / 进度条** | 逐张照片**先各自评级**，再对等级求平均 | 规避「大量干净照片摊薄重污损」，对应缺陷 7047861151 |

→ **新增待确认项 T7**：整表修改（按 line 批量改海生物/油漆比例）触发等级重算时落到哪套口径？「部位级先平均比例」与「逐照片评级后平均」会得出不同的 R0–R4。

另有两套等级不得与 R0–R4 混称：**边缘侧污损网格 6 档**（无数据/干净/微观/宏观轻/宏观中/宏观重）、**作业任务人工录入 3 档**（1 轻/2 中/3 重）。

### 9.2 检测报告页面既有的 line 维度（整表修改的落点）

`运营后台页面交互逻辑文档` §检测报告 给出既有页面结构——整表修改不是新建维度，而是挂在已有的「检测线」上：

- 部位页签：**船图 / 左侧板 / 右侧板 / 底板 / 螺旋桨 / 特殊部位**（船图固定，其余按出动任务动态展示）。
- 检测线 **L1-Ln**（数量读作业配置），切换检测线后当前 line 的**照片 / 评级 / 漆面结果 / 审核状态**同步刷新。
- **审核控制针对当前 line**：免审 / 待审核 / 审核通过只作用于当前选中 line，同一部位不同 line 可不同状态；**审核通过的 line 锁定编辑**（照片操作层隐藏、结论不可改）。
- 底部固定操作区：结束作业 / 预览PDF / 发布完整报告。
- **空 line 手动添加照片**：点击后按吃水生成深度占位行，上传照片后自动生成污损等级/污染物组成/漆面结果（与评论 #2「未上传图片部位」相关）。

→ 推论：整表修改入口应落在「检测线」维度，且必须与「审核通过的 line 锁定」联动（审核通过后整表修改也应只读）。

### 9.3 术语统一

同一机制在正式文档里有三种叫法，需统一：**修改日志**（NOS）、**重判记录**（产品线依赖地图）、**人工修正记录**（业务逻辑文档）。语义一致：人工改海生物/油漆标注 → **追加记录（非覆盖）** → 读取时回放 → 重算等级。`NOS 产品说明文档.md:784` 补充：报告页人工修改海生物标注会记成「修改日志」叠加在 AI 结果之上，评级由代码重算；**且「修改前后数据」会进 AI 反馈队列供模型迭代**——批量整表修改同样会产生这条 AI 反馈数据流。

「重建报告」红线再次印证：刷新结论时先删报告文档再按默认值重建，**分区编辑记录、审核结果、重判记录全部丢失**（见 `README.md:318/350`、`产品线依赖地图.md` §4，均为「地4/运6」口径）。
