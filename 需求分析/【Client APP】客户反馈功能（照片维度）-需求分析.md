## 1. 项目概览

### 1.1 背景与目标

客户 ONE 在查看检测照片时，希望对识别结果提供反馈。需求包含两个交付面：

1. Client APP 在单张照片上收集海生物识别、漆况识别的准确/不准确反馈，并在再次进入时恢复当前反馈状态。
2. mobi 后台 AM 配置中心新增反馈列表，让管理员和对应客户的 AM 查看、筛选、放大及下载反馈照片。

### 1.2 当前状态

- 优先级：P1。
- 规划及实际上车版本：`[软件]260815`。
- 当前节点：室内/测试环境测试。
- 评论显示代码已合并并应自动部署，但未提供部署成功通知、构建号和完整提测版本矩阵。

## 2. 需求萃取

### 2.1 业务需求

#### 已确认需求

- 客户可对单张照片的海生物识别和漆况识别反馈“准确/不准确”。
- APP 能读取每个维度的当前反馈结果；未反馈维度不在接口响应中出现。
- 内部后台展示照片级反馈，便于管理员和 AM 查看客户反馈。
- 后台列表支持客户名称筛选、mobi ID 精确检索和组织级权限隔离。

#### 未确认核心规则

1. 同照片同维度重复反馈是追加多条历史还是覆盖当前状态。
2. 选择“是/准确”是否也立即提交反馈。
3. 客户名称筛选的业务对象是客户组织、客户账号还是反馈人。

### 2.2 用户需求

| 角色 | 任务 | 范围 |
|---|---|---|
| 客户 APP 用户 | 在有权限访问的照片上提交两个维度的准确/不准确反馈，并查看当前状态 | 当前账号可访问的 mobi/照片 |
| 管理员 | 查看和筛选全部客户反馈，放大或下载原图 | 全部组织 |
| `am_admin` | 技术方案定义为查看全部反馈 | 需产品确认是否等同管理员 |
| 主/辅 AM | 查看自己负责客户组织的反馈 | `user_ext_am` 绑定组织 |
| 其他内部用户 | 不允许访问列表或反馈数据 | 无权限 |

### 2.3 功能需求

#### APP 照片反馈

- 图片详情提供海生物识别是/否、漆况识别是/否四种操作。
- 写接口：`POST /api/client-app/v1/photo/feedback`。
- 请求字段：
  - `mobi_photo_id`：照片 ID，int64，必填。
  - `feedback_type`：1=海生物识别，2=漆况识别。
  - `accurate`：1=准确，2=不准确。
- 服务端从照片反查真实 mobi 并校验当前用户权限，不接收客户端自行声明的 mobi ID。
- `inspection_report` 的照片分类数据增加：
  - `biofouling_feedback`：1=准确，2=不准确。
  - `paint_feedback`：1=准确，2=不准确。
  - 未反馈时字段整体省略。

#### mobi 后台反馈列表

- 入口：AM 配置中心新增客户 APP 反馈列表。
- 展示：mobi ID、船名、反馈时间、反馈照片、一级/二级/三级部位及侧板水尺、反馈人、反馈内容。
- 图片：缩略图展示，点击放大，支持下载原图。
- 筛选：
  - mobi ID 精确查询。
  - 客户名称模糊搜索后转换为 ID 过滤；实际 ID 类型待确认。
  - 多条件按 AND 组合是技术实现推导，产品未单独确认。
- 分页：默认 `current=1`、`pageSize=20`，最大值和非法值行为未定义。
- 权限：管理员/`am_admin` 全量；普通 AM 仅名下组织；AM 无负责客户返回空页；其他角色报无权限。

### 2.4 非功能需求

#### 已确认约束

- 写反馈必须做服务端照片归属和用户权限校验。
- 后台数据必须服务端按组织过滤。
- `inspection_report` 应批量合并反馈，避免三个调用点重复实现。
- 数据库按照片 ID、反馈类型建唯一键的方案只适用于“覆盖最新”口径。
- mobi ID 和 organization ID 应有查询索引。

#### 测试推导、待确认

- 写接口和列表查询的 P95 响应时间、超时、最大数据量。
- 写反馈的幂等、并发相反提交和失败恢复。
- 缩略图/原图鉴权、有效期、过期重签名与下载失败处理。
- 多表补全的 N+1 风险、关联数据缺失降级和错误监控。
- 反馈操作日志、敏感 URL/JWT 脱敏和数据保留策略。

## 3. 分析与评价

### 3.1 完整性

主流程已覆盖 APP 提交、报告回显、后台列表、筛选和权限。但以下必要分支没有形成验收规则：

- APP 提交中、成功、失败、超时、断网、会话过期。
- 并发/重复提交和相反结果的胜出规则。
- 后台无负责客户、筛选无结果、关联数据缺失和图片加载失败。
- 分页参数边界、搜索边界、最大数据量和浏览器兼容。
- 照片/出动软删除后的反馈可见性。

### 3.2 一致性

#### 一致项

- 两个反馈维度及 1/2 枚举在技术方案和接口附件中一致。
- mobi ID 只做精确查询，产品评论、接口附件和既有用例一致。
- APP 权限基于照片真实归属，后台权限基于组织，安全方向合理。

#### 冲突项

| 优先级 | 冲突 | 影响 |
|---|---|---|
| 🔴 | 产品评论“追加多条” vs 技术方案“upsert 覆盖” | 表结构、列表条数、历史、时间、APP 回显 |
| 🔴 | 技术方案“是/否都提交” vs XMind“是，不提交” | APP 主流程、接口调用、现有用例 |
| 🔴 | “客户名称” vs 接口 `userId` | 筛选对象、重名、多账号、权限 |
| 🔴 | `create_at` vs `update_at` | 反馈时间和默认排序 |
| 🟡 | 原需求管理员/主辅 AM vs 技术方案增加 `am_admin` | 角色入口和数据范围 |

### 3.3 合理性

#### 合理点

- 不信任客户端 mobi ID，可防止伪造归属越权。
- 按反馈类型拆行使类型可扩展，三态读模型简洁。
- 查询统一在批量分类入口合并，降低遗漏风险。
- `organization_id` 冗余和索引适合后台高频组织过滤。

#### 风险点

- APP 没有提交反馈的明确 UI 状态，存在“无反馈操作”反模式。
- 后台入口规则未定，可能出现“先显示后拦截”。
- 空态和错误态未设计，用户无法区分无数据、无客户、无权限和加载失败。
- 客户名称依赖另一接口却未写入正式流程，形成隐式依赖。

### 3.4 量化性

当前只量化了分页默认值和接口枚举。建议作为评审基线、待确认的指标包括：

- 普通写/查请求 P95 小于 500ms。
- 列表默认 20 条，pageSize 建议上限 100。
- 客户实时搜索建议约 300ms 防抖，结果上限需明确。
- 提交请求发出后立即禁用按钮，直到成功或失败。
- 大量反馈按万级数据验证索引、分页和内存。
- 时间统一到秒并携带明确时区。

以上均为经验建议，不是原始确认需求。

### 3.5 逻辑闭环

单照片、单反馈维度的预期状态为：未反馈、准确、不准确；准确与不准确可互相切换。但闭环仍缺：

- 切换是覆盖还是追加。
- “是”是否真正写入。
- 修改后反馈时间如何变化。
- 写成功后 APP 何时读取到新状态。
- 删除照片/反馈后状态如何恢复。

## 5. 评审意见

### 5.1 评审结论

**结论：有条件通过。**

技术实现方向可行，安全和查询设计有较好基础；但三项核心规则冲突会改变数据模型和主要验收预期，必须先确认再把工作项视为“可稳定测试”。

### 5.2 产品经理需优先确认

1. 重复反馈追加还是覆盖。
2. “是/准确”是否提交及成功提示。
3. 客户名称筛选对象和重名处理。
4. 首次/最近反馈时间的展示与排序。
5. 角色入口与数据范围矩阵。
6. APP 最终入口和交互稿。
7. 失败、超时、会话过期和空态。
8. 导出、统计、算法消费是否属于本期。

### 5.3 开发需优先确认

1. 测试环境实际表结构与重复反馈实现。
2. `accurate=1` 是否真实落库，APP 是否发起请求。
3. 客户搜索接口和 userId 的真实业务实体。
4. create_at/update_at 的实际展示和排序。
5. 稳定错误码、并发行为及真实 JSON 省略字段样例。
6. 三条报告构建路径是否全部覆盖且无 N+1。
7. 多表补全、图片鉴权和关联数据缺失策略。
8. APP、后台、Server、数据库脚本的成套提测版本。

### 5.4 回归范围

- APP 图片详情：作业状态、布局、反馈四态、未反馈/单维度/双维度/修改、网络与会话异常。
- 写接口：参数、照片归属、权限、幂等、并发、数据库约束和错误码。
- `inspection_report`：字段省略、所有构建路径、旧客户端兼容和性能。
- 后台：入口、角色、客户/mobi 筛选、分页排序、空态、图片查看下载。
- 数据：追加/覆盖模型、时间、软删除、关联缺失、多表补全和索引。
- 安全：跨客户照片、跨组织筛选、图片 URL、非 AM 访问和日志脱敏。

### 5.5 既有用例处置

现有 46 条用例不能直接全部作为验收基线：

- 必须重写“是-不提交反馈”相关用例。
- 客户筛选应拆成名称搜索与 ID 过滤两层。
- 排序用例需等待时间口径确认。
- URL 参数保持和未确认额外筛选应降为建议，不应直接判缺陷。
- 需补充接口异常、越权、并发、字段省略、数据缺失和图片 URL 安全覆盖。

### 5.6 评审会发言稿速查

1. 产品评论说重复反馈追加，技术方案说覆盖，先请产品选定一种。
2. 技术接口说“是/否”都提交，但旧用例说“是”不提交，需要统一。
3. 页面要按客户名称筛选，接口却收 userId，请确认筛选对象。
4. 重复修改后显示首次时间还是更新时间，默认排序跟哪个字段。
5. 请给 admin、am_admin、主 AM、辅 AM 的完整权限矩阵。
6. 请补 APP 提交中、失败、超时、会话过期的交互。
7. 请给成套提测版本和部署成功证明。
8. 请开发证明三个报告路径都带反馈字段且没有 N+1。
9. 图片放大和下载 URL 也必须做组织权限和过期处理。
10. 核心口径确认后先修订 46 条旧用例，再执行正式回归。
